Módulo 13

Where Data Is Stored

Entendendo o Kernel Linux, pseudo-sistemas de arquivos e a hierarquia de diretórios.

13.1 Introdução

Lembrete Importante: Quando a maioria das pessoas se refere ao "Linux", elas estão, na realidade, falando de uma combinação de softwares chamada GNU/Linux, que define o sistema operacional completo. O GNU é o conjunto de software livre que envolve o kernel e fornece equivalentes de código aberto para muitos comandos comuns do UNIX. A parte Linux dessa combinação é o Kernel Linux, que constitui o núcleo do sistema operacional. O kernel é carregado no momento da inicialização (boot time) e permanece em execução contínua para gerenciar cada aspecto do funcionamento do sistema.

Subsistemas do Kernel

Uma implementação do kernel Linux inclui múltiplos subsistemas que fazem parte do próprio núcleo, além de outros componentes que podem ser carregados de forma modular (módulos do kernel) quando necessários. As funções essenciais do kernel Linux abrangem:

  • Interface de Chamadas de Sistema (System Call Interface): O canal de comunicação entre os programas do usuário e o kernel.
  • Gerenciamento de Processos (Process Management): Criação, execução e finalização de programas e tarefas.
  • Gerenciamento de Memória (Memory Management): Alocação e controle do uso da RAM e Swap.
  • Sistemas de Arquivos Virtuais (Virtual Filesystems): Abstração que unifica a manipulação de diferentes sistemas de armazenamento.
  • Rede (Networking): Gerenciamento de protocolos e tráfego de dados de rede.
  • Drivers de Dispositivos (Device Drivers): Softwares de controle dos componentes de hardware.

Em resumo, por meio de um shell (terminal), o kernel aceita comandos do usuário e gerencia os processos encarregados de realizar esses comandos, concedendo-lhes acesso controlado a dispositivos como memória, discos, interfaces de rede, teclados, mouses, monitores e muito mais.

Organização e Estrutura

Um sistema Linux típico possui milhares de arquivos. O Filesystem Hierarchy Standard (FHS) fornece uma diretriz padronizada para as distribuições sobre como organizar esses arquivos de forma consistente dentro do disco.

Ao longo deste capítulo, será fundamental compreender o papel do kernel Linux e como ele processa e disponibiliza informações em tempo real sobre o status do sistema por meio dos pseudo-sistemas de arquivos /proc e /sys.

13.2 Processos e o Diretório /proc

O kernel fornece acesso a informações em tempo real sobre os processos ativos por meio de um pseudo-sistema de arquivos que fica visível sob o diretório /proc. De forma complementar, os dispositivos de hardware são disponibilizados como arquivos especiais sob o diretório /dev, enquanto informações detalhadas sobre esses dispositivos podem ser encontradas em outro pseudo-sistema de arquivos sob o diretório /sys.

Os pseudo-sistemas de arquivos parecem arquivos reais armazenados no disco rígido, mas existem apenas na memória RAM. A maioria deles, como o /proc, é projetada para parecer uma árvore hierárquica contendo subdiretórios e arquivos que partem da raiz (/) do sistema, mas são apenas estruturas virtuais mantidas pelo kernel na memória volatil.

Anatomia do Diretório /proc

O diretório /proc não armazena apenas dados sobre os processos em execução, como o nome sugere. Ele também contém relatórios completos sobre o hardware da máquina e as configurações atuais do kernel.

Muitos comandos essenciais do Linux lêem e extraem dados desse diretório para funcionar, como o top, free, mount, umount, entre outros. Sendo assim, raramente um administrador precisa garimpar o /proc manualmente — é muito mais prático e amigável utilizar os comandos que já fazem essa abstração.

Veja um exemplo de listagem do diretório /proc:

sysadmin@localhost:~$ ls /proc

39         driver       kmsg         partitions    timer_stats
60         execdomains  kpagecgroup  sched_debug   tty
72         fb           kpagecount   schedstat     uptime
acpi       filesystems  kpageflags   scsi          version

A listagem revela pastas nomeadas com textos e outras com números. Cada número corresponde ao ID de um processo ativo (PID) no sistema. Por exemplo, o diretório indicado pelo número 72 representa o PID 72, um programa em execução. Dentro dessa pasta existem subarquivos que descrevem o consumo de memória, permissões e variáveis de ambiente daquele processo específico. Em um sistema Linux ativo, sempre existirá o **PID 1** (o processo de inicialização do sistema).

Arquivos Globais do Kernel em /proc

Além dos diretórios numéricos dos processos, o /proc possui arquivos de texto regulares com dados globais sobre o kernel em execução:

Arquivo Conteúdo Mapeado
/proc/cmdline Parâmetros e instruções especiais passados para o kernel no momento da inicialização (boot).
/proc/meminfo Estatísticas detalhadas sobre o uso e distribuição da memória RAM e Swap do sistema.
/proc/modules Lista de todos os módulos extras (drivers dinâmicos) atualmente carregados no kernel.

Ajustando o Kernel em Tempo de Execução (/proc/sys)

Enquanto a maior parte dos arquivos do /proc é estritamente de leitura (mesmo para o superusuário), os arquivos localizados dentro do subdiretório /proc/sys **podem ser modificados pelo usuário root**. Alterar esses arquivos modifica o comportamento do kernel Linux imediatamente e em tempo de execução.

Mudanças Temporárias: Modificar os arquivos sob o diretório /proc/sys altera o kernel de forma volátil, ou seja, as configurações se perdem ao reiniciar o computador. Para tornar as alterações permanentes (persistentes), as regras devem ser escritas dentro do arquivo de configuração /etc/sysctl.conf.

Exemplo Prático: Desativando a resposta a comandos de Ping (ICMP)

O arquivo /proc/sys/net/ipv4/icmp_echo_ignore_all controla se o sistema responde a requisições de rede ICMP. O valor padrão 0 significa que o sistema responderá ao ping. Alterar esse valor para 1 fará o kernel ignorar os pings silenciosamente: 

sysadmin@localhost:~$ su -
Password: 
root@localhost:~# cat /proc/sys/net/ipv4/icmp_echo_ignore_all 
0
root@localhost:~# ping -c1 localhost
PING localhost.localdomain (127.0.0.1) 56(84) bytes of data.
64 bytes from localhost.localdomain (127.0.0.1): icmp_seq=1 ttl=64 time=0.026 ms
 
--- localhost.localdomain ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.026/0.026/0.026/0.000 ms

root@localhost:~# echo 1 > /proc/sys/net/ipv4/icmp_echo_ignore_all
root@localhost:~# ping -c1 localhost
PING localhost.localdomain (127.0.0.1) 56(84) bytes of data.

1 packets transmitted, 0 received, 100% packet loss, time 10000ms

13.2.1 Hierarquia de Processos

Assim que o kernel conclui seu carregamento durante o procedimento de boot, ele inicia o processo primordial do sistema, chamado init, atribuindo-lhe obrigatoriamente o PID 1. A partir daí, este processo inicial se encarrega de disparar todos os demais processos do sistema, e cada nova tarefa ganha um ID de processo (PID) em ordem sequencial.

Nota de Arquitetura: Em sistemas baseados no padrão tradicional System V, o processo init aponta para o binário /sbin/init. Já em sistemas modernos baseados em systemd, o arquivo executado é o /bin/systemd (que quase sempre é um link simbólico para o executável /lib/systemd/systemd). Independentemente da tecnologia adotada pela distribuição, os dados operacionais desse processo raiz sempre estarão mapeados no diretório /proc/1.

Relação de Parentesco: Parents e Children

À medida que o processo inicial ativa novos serviços, estes, por sua vez, podem abrir novos sub-processos em uma cadeia contínua. Quando um processo gera outro, o iniciador é denominado processo pai (parent process) e o novo processo criado é o processo filho (child process). Nas ferramentas de monitoramento do sistema, o ID do processo pai é identificado pela sigla PPID (Parent Process ID).

Quando o computador permanece ligado por muito tempo, a numeração sequencial pode eventualmente atingir o limite máximo de PIDs suportado pelo sistema. Esse teto pode ser verificado e ajustado por meio do arquivo /proc/sys/kernel/pid_max. Ao alcançar esse limite, o sistema realiza uma rotação automática (roll over), voltando a reaproveitar de forma transparente os números menores que foram liberados no início da escala.

Visualizando a Árvore de Processos com o pstree

Todos os processos do Linux podem ser mapeados visualmente em uma árvore genealógica de acoplamentos. Para inspecionar essa estrutura hierárquica diretamente no terminal, utilizamos o comando pstree: 

sysadmin@localhost:~$ pstree
init-+-cron
     |-login---bash---pstree
     |-named---18*[{named}]
     |-rsyslogd---2*[{rsyslogd}]
     `-sshd

Analisando o retorno do comando acima, podemos rastrear e descrever com precisão as relações de dependência da seguinte forma:

Processo Origem (Pai) Relação Lógica Processo Destino (Filho)
init é o pai direto de login
login é o filho de init
login é o pai de bash
bash é o filho de login
bash é o pai de pstree
pstree é o filho de bash

13.2.2 Capturando um Snapshot de Processos

Outra maneira muito comum de inspecionar os processos em execução é utilizando o comando ps. Por padrão, se executado sem parâmetros adicionais, o ps exibe apenas as tarefas ativas vinculadas à sessão de terminal (shell) corrente. Ironicamente, mesmo que o seu objetivo seja listar outros processos, o próprio comando ps inclui a si mesmo no resultado gerado: 

sysadmin@localhost:~$ ps
  PID TTY          TIME CMD
 6054 ?        00:00:00 bash
 6070 ?        00:00:01 xeyes
 6090 ?        00:00:01 firefox
 6146 ?        00:00:00 ps

Renderizando Árvores com o parâmetro --forest

Se você executar o comando ps acompanhado da opção --forest, o terminal exibirá linhas e ramificações gráficas indicando de forma explícita o parentesco (pai e filho) entre os processos, de maneira muito parecida com o que o comando pstree realiza: 

sysadmin@localhost:~$ ps --forest
  PID TTY          TIME CMD
 6054 ?        00:00:00 bash
 6090 ?        00:00:02   \_ firefox
 6180 ?        00:00:00   \_ dash
 6181 ?        00:00:00        \_ xeyes
 6188 ?        00:00:00        \_ ps

Estratégias de Filtragem e Paginação

Caso o comando não seja filtrado, você terá que rolar manualmente por centenas de linhas para encontrar o processo desejado. Uma forma altamente eficiente de reduzir essa verbosidade é utilizar o comando grep acoplado por um pipe para isolar palavras-chave específicas (como o nome de uma aplicação): 

sysadmin@localhost:~$ ps -ef | grep firefox
 6090 pts/0    00:00:07 firefox

Outra alternativa indispensável para tornar a leitura humana muito mais confortável e controlável é direcionar a saída bruta para um paginador interativo de terminal utilizando o comando less (ex: ps aux | less).

Filtrando Processos por Usuário

Em ambientes multiusuário, um administrador frequentemente precisa monitorar de perto apenas os processos pertencentes a uma conta específica. O comando ps oferece suporte a diferentes estilos de opções para realizar esse filtro. Para adotar o padrão tradicional do UNIX, utilize o modificador -u seguido do nome do usuário alvo: 

sysadmin@localhost:~$ ps -u root
  PID TTY          TIME CMD
    1 ?        00:00:00 init
   13 ?        00:00:00 cron
   15 ?        00:00:00 sshd
   43 ?        00:00:00 login

13.2.3 Monitoramento de Processos em Tempo Real

Enquanto o comando ps fornece um instantâneo estático (snapshot) dos processos rodando no exato momento em que o comando é disparado, o comando top disponibiliza uma interface dinâmica baseada em tela que atualiza regularmente a listagem dos processos ativos. O comando é executado da seguinte forma: 

sysadmin@localhost:~$ top

Por padrão, a saída do comando top é classificada automaticamente pela porcentagem de uso da CPU (%CPU). Os processos que estão demandando mais capacidade de processamento são posicionados no topo da lista:

Intervenções Administrativas: Finalização e Prioridades

Manter o top em execução contínua permite monitorar a estabilidade do sistema. Se um processo perder o controle e começar a monopolizar os recursos do hardware, ele subirá imediatamente para o topo da lista. O administrador pode tomar duas ações corretivas em tempo real:

Tecla Ação Executada Comportamento Técnico
K Kill (Terminar Processo) Solicita o PID do processo e o número do sinal. Enviar o sinal padrão solicita o encerramento amigável, enquanto o sinal 9 (SIGKILL) força o término imediato.
R Renice (Alterar Prioridade) Ajusta o fator de prioridade (niceness) do processo, variando em uma escala estrita de -20 a 19.

Regras de Prioridade (Niceness):

  • Valores negativos ou menores que o atual aumentam a prioridade do processo (ele se torna "menos gentil" com os outros, exigindo mais tempo de CPU). Apenas o usuário root possui permissão para definir prioridades mais altas (valores negativos).
  • Valores positivos ou maiores reduzem a prioridade do processo (ele se torna "mais gentil", cedendo espaço na CPU). Qualquer usuário comum pode reduzir a prioridade de suas próprias tarefas.

Decodificando a Média de Carga (Load Average)

A primeira linha informada pelo top apresenta o Load Average (Média de Carga), que aponta a tendência de uso da CPU nos últimos 1, 5 e 15 minutos. Esses mesmos dados podem ser extraídos por meio do comando uptime ou inspecionando o arquivo pseudo-sistema /proc/loadavg: 

sysadmin@localhost:~$ cat /proc/loadavg
0.12 0.46 0.25 1/254 3052

A estrutura do arquivo /proc/loadavg divide-se em três blocos de dados essenciais:

1. Médias de Carga (Três primeiros valores)

No exemplo, 0.12, 0.46 e 0.25 são as médias de carga. Esses números são proporcionais à quantidade de núcleos de CPU da máquina. Em uma CPU single-core, a carga 1.00 indica 100% de ocupação. Em uma CPU quad-core (4 núcleos), a carga 1.00 indica que apenas 25% da capacidade total de processamento está comprometida.

2. Fração de Processos (Quarto valor)

O valor formatado como fração (1/254) revela a quantidade de processos executando código na CPU neste exato instante (1) em relação ao total de processos gerenciados pelo kernel no momento (254).

3. Último PID Ativado (Quinto valor)

O número final (3052) identifica o PID mais recente a receber ciclos de processamento e executar código na CPU.

Monitoramento de Memória em Tempo Real

Outro fator crucial para manter o comando top em execução é o monitoramento volátil da memória RAM e do Swap. Juntamente com a saída do comando free, o cabeçalho do top detalha o consumo geral de buffers e cache.

A tabela dinâmica também apresenta a coluna %MEM individualizada por processo. Isso permite que administradores identifiquem com rapidez anomalias e processos com vazamento de memória (memory leak) antes que comprometam a estabilidade do sistema de arquivos.

13.3 Gerenciamento de Memória

A memória em um sistema Linux moderno é governada e gerenciada inteiramente pelo kernel. A memória RAM física instalada é compartilhada entre todos os processos ativos por meio de um método avançado chamado endereçamento virtual (virtual addressing).

O endereçamento virtual permite que múltiplos processos acessem a memória de forma simultânea, isolada e sem conflitos ou travamentos (crashes). Ele realiza isso mapeando ponteiros lógicos para blocos físicos e, quando necessário, aloca áreas do disco rígido (a memória swap) para atuarem como uma extensão da RAM.

A memória é fragmentada em blocos de unidades de tamanho idêntico (páginas de memória) que podem ser indexadas como qualquer outro recurso. O kernel é tão flexível que consegue gerenciar não apenas barramentos de memória locais, mas também acessar memórias localizadas remotamente — seja em outro servidor, em um dispositivo virtualizado ou até mesmo em volumes compartilhados fisicamente em outro continente!

Divisão Espacial: Kernel Space vs User Space

Embora uma análise profunda sobre a arquitetura de paginação do Linux vá além do escopo deste nível introdutório, é fundamental compreender a separação conceitual e física entre o Kernel Space e o User Space:

Kernel Space (Espaço do Kernel)

Região protegida e isolada da memória onde o código principal do kernel é carregado e executado com privilégios máximos de hardware (Ring 0). Processos comuns com níveis de privilégio inferiores não conseguem acessar ou sobrescrever essa área sob nenhuma hipótese.

User Space (Espaço do Usuário)

Área da memória disponibilizada para as aplicações de prateleira, shells, servidores web e programas disparados pelos usuários comuns do sistema.

Os programas rodando no User Space não possuem permissão para tocar diretamente no hardware ou no Kernel Space. Quando um software precisa ler um arquivo no disco ou enviar um pacote pela rede, ele é obrigado a fazer uma requisição formal ao núcleo através das Chamadas de Sistema (System Calls), que funcionam como APIs intermediárias altamente controladas.

Resiliência do Sistema: Esse mecanismo rigoroso de isolamento impede que um programa instável, mal projetado ou malicioso em espaço de usuário consiga derrubar ou corromper as funções vitais do sistema. É justamente essa arquitetura que confere aos ambientes Linux a alta estabilidade e resiliência exigidas em servidores de produção.

13.3.1 Inspecionando o Consumo de Memória

A execução do comando free sem nenhuma opção adicional fornece um instantâneo (snapshot) exato da utilização da memória no momento em que o terminal processa a linha de comando. Sem modificadores, as estatísticas de saída são exibidas na unidade padrão de kilobytes (KB): 

sysadmin@localhost:~$ free
             total       used       free     shared    buffers     cached       
Mem:      32953528   26171772    6781756          0       4136   22660364    
-/+ buffers/cache:    3507272   29446256                                        
Swap:            0          0          0

Para facilitar a leitura humana e a interpretação imediata dos dados apresentados, as opções -m (exibição em megabytes) ou -g (exibição em gigabytes) tornam-se indispensáveis para simplificar a análise dos blocos de memória.

Monitoramento Contínuo com Intervalos Temporais

Caso precise monitorar a oscilação do uso da RAM ao longo do tempo (por exemplo, durante a execução de uma tarefa pesada de compilação ou renderização), você pode passar o parâmetro -s seguido da quantidade de segundos em que a tela deve se atualizar. O comando abaixo renovará os dados a cada 10 segundos: 

sysadmin@localhost:~$ free -s 10
              total        used        free      shared  buff/cache   available
Mem:      132014640    47304084    77189512        3008     7521044    84085528
Swap:     134196220       42544   134153676

              total        used        free      shared  buff/cache   available
Mem:      132014640    47302928    77190668        3008     7521044    84086684
Swap:     134196220       42544   134153676

Decodificando as Linhas do Comando free

Para ler corretamente a matriz gerada pelo comando, precisamos compreender o papel de cada uma de suas linhas estruturais:

1. Cabeçalho Descritivo (Descriptive Header)

Mapeia as colunas de medição: capacidade total (total), quantidade em uso (used), espaço completamente limpo (free), buffers e caches mapeados.

2. Estatísticas de Memória Física (Physical Memory Statistics)

A linha iniciada por Mem: aponta os valores brutos lidos pelo kernel diretamente dos pentes físicos de RAM instalados na placa-mãe.

3. Linha de Ajuste Técnico (-/+ buffers/cache)

Representa o cálculo real de memória física livre após desconsiderar o espaço temporário utilizado pelo kernel para fins de cache de arquivos. No Linux, a memória alocada para cache é considerada "usada", mas ela pode ser imediatamente desalocada e reaproveitada (reclaimed) pelas aplicações caso haja necessidade instantânea.

4. Memória Swap / Virtual

A linha final (Swap:) detalha o uso do espaço de paginação configurado no disco rígido. Ela cria a ilusão técnica de que o computador possui mais memória do que a capacidade física real instalada, embora seu uso excessivo degrade consideravelmente o tempo de resposta e a velocidade geral do sistema.

O Mecanismo OOM Killer (Out Of Memory)

Se o volume de memória RAM livre e o espaço de swap disponível atingirem níveis criticamente baixos, o kernel Linux ativará uma rotina interna de emergência de salvaguarda chamada OOM Killer. Este mecanismo começará a **derrubar e finalizar processos automaticamente** para evitar o travamento completo do hardware.

Ação Preventiva do Administrador: Para evitar que o OOM Killer escolha de forma arbitrária e finalize um serviço crítico em produção (como um servidor web ou banco de dados), o administrador deve monitorar o sistema de perto utilizando as ferramentas top ou free, intervindo manualmente com o comando kill para encerrar processos secundários de sua própria escolha antes que o sistema entre em colapso.

13.4 Arquivos de Log (Log Files)

À medida que o kernel e os vários processos rodam no sistema, eles produzem saídas textuais que descrevem seu status operacional. Algumas dessas mensagens são exibidas diretamente como saída padrão (STDOUT) ou erro padrão (STDERR) no terminal. No entanto, grande parte desses dados não é enviada para a tela, sendo gravada em arquivos persistentes no disco. Essas informações são chamadas de mensagens de log ou dados de auditoria.

Os arquivos de log são indispensáveis para a administração de sistemas por dois motivos principais: eles ajudam a **solucionar problemas técnicos** (troubleshooting) e permitem auditar se acessos não autorizados ou brechas de segurança foram tentados contra a máquina.

Alguns processos possuem mecanismos internos para gravar seus próprios logs em arquivos dedicados, enquanto outros dependem de um serviço independente rodando em segundo plano (um daemon) encarregado exclusivamente de centralizar e gerenciar as mensagens do sistema.

Nota de Nomenclatura: O termo Syslog é usado quase de forma genérica para descrever o subsistema de log em ambientes Linux devido ao seu longo histórico no ecossistema. Muitas vezes, quando uma documentação cita "syslog", ela está se referindo genericamente a qualquer mecanismo de logging que esteja ativo na distribuição atual.

A Evolução dos Daemons de Log

A arquitetura dos daemons de gerenciamento de logs varia de acordo com a idade e a concepção da distribuição Linux:

Modelo Tradicional (syslogd + klogd)

Sistemas antigos utilizavam dois daemons trabalhando em conjunto: o syslogd (para logs de aplicações em espaço de usuário) e o klogd (dedicado exclusivamente a interceptar logs vindos do kernel).

Modelo Centralizado (rsyslogd)

Nas distribuições modernas, o serviço rsyslogd substitui o modelo antigo, unificando as funções de ambos em um único daemon altamente performático e expansível.

Modelo Moderno systemd (journald)

Em distribuições baseadas no gerenciador systemd, o daemon de logging nativo chama-se journald. Seus arquivos contêm dados estruturados textuais e binários de alta performance. O utilitário padrão e obrigatório para inspecionar esses registros é o comando journalctl.

Mapa de Logs Comuns em /var/log

Independentemente do daemon ativo, os arquivos de log são quase sempre armazenados dentro da estrutura do diretório /var/log. Veja abaixo a tabela dos arquivos mais comuns e seus respectivos escopos:

Arquivo de Log Conteúdo Registrado
boot.log Mensagens geradas à medida que os serviços do sistema são inicializados durante o boot.
cron Registros produzidos pelo daemon crond detalhando a execução de tarefas agendadas e recorrentes.
dmesg Mensagens e diagnósticos puros capturados pelo kernel durante a inicialização do hardware.
maillog Informações de depuração geradas pelos servidores e daemons de e-mail (envios e recebimentos).
messages Log genérico do sistema para o kernel e processos que não possuem um arquivo próprio. Em algumas distribuições, este arquivo é nomeado como syslog.
secure Registros críticos que exigem autorização ou autenticação de segurança (como tentativas de login e uso do comando sudo).
journal/ Diretório de mensagens estruturadas do serviço padrão systemd-journald.service.
Xorg.0.log Mensagens e erros emitidos pelo servidor gráfico de janelas X Windows (GUI).

Métodos de Visualização e Análise

Existem dois métodos principais para inspecionar os arquivos mapeados em /var/log:

Método 1: Comandos de Texto Puro (cat / less)

Para arquivos de texto simples, você pode listar seu conteúdo bruto com cat ou usar o paginador less, que viabiliza pesquisas por termos e rolagem confortável das páginas.

Método 2: Utilitário de Sistema (journalctl)

Em sistemas modernos, os dados de /var/log/journal contêm metadados indexados e estruturas binárias. Tentar ler esses arquivos com cat ou less causará anomalias de formatação e caracteres ilegíveis na tela por causa dos códigos de controle. Portanto, o uso do comando journalctl é obrigatório para interpretar o diário binário com segurança.

O Mecanismo de Rotação de Logs (Log Rotation)

Como o sistema opera ininterruptamente, os logs acumulariam gigabytes de dados rapidamente, esgotando o espaço em disco. Para mitigar isso, o Linux realiza a rotação de logs (log rotation), rotina automatizada que renomeia e compacta arquivos antigos, abrindo espaço para registros novos.

Os arquivos rotacionados recebem um sufixo numérico ou uma marcação de data ao final do nome:

sysadmin@localhost:~$ ls /var/log/secure*
/var/log/secure  /var/log/secure.0  /var/log/secure-20261103

Essa rotina geralmente ocorre de forma agendada (ex: semanalmente). O sistema interrompe momentaneamente a escrita no arquivo principal, adiciona o sufixo de data (ex: -20261103), gera um arquivo limpo com o nome original (ex: secure) e retoma a gravação imediatamente através dele.

Auditando Logs Binários Especiais (wtmp / btmp)

Embora a maior parte dos arquivos em /var/log seja texto legível, registros específicos de contabilidade do sistema são salvos nativamente em formato binário de dados. Podemos checar essa assinatura utilizando o comando file: 

sysadmin@localhost:~$ file /var/log/wtmp
/var/log/wtmp: data

O retorno classificado como data comprova que o arquivo é binário. Para ler e extrair relatórios legíveis dessas mídias sem quebrar o terminal, o Linux disponibiliza comandos tradutores específicos:

Comando Dedicado Arquivo Alvo Binário Relatório Extraído
last /var/log/wtmp Apresenta o histórico completo de logins e logouts bem-sucedidos realizados na máquina.
lastb /var/log/btmp Lista de forma minuciosa todas as **tentativas de login que falharam** (essencial para rastrear ataques de força bruta).
Acesso Restrito: Devido ao seu caráter crítico de auditoria de segurança, o comando lastb exige obrigatoriamente privilégios administrativos de superusuário (root ou uso do prefixo sudo) para ser executado no console.

13.5 Mensagens do Kernel (Kernel Messages)

O arquivo /var/log/dmesg armazena as mensagens e diagnósticos gerados pelo kernel durante a inicialização (startup) do sistema. De forma complementar, o arquivo /var/log/messages (ou /var/log/syslog) registra as mensagens emitidas pelo kernel com o sistema já operacional e em execução, embora esses registros fiquem misturados com notificações vindas de outros daemons e processos em segundo plano.

Embora o kernel Linux não possua um arquivo de log isolado por padrão para sua rotina operacional diária, um administrador pode configurar um destino exclusivo modificando as regras de triagem dentro dos arquivos de configuração /etc/syslog.conf ou /etc/rsyslog.conf.

O Anel de Buffer do Kernel (Kernel Ring Buffer)

Para inspecionar o status do núcleo em tempo real, utilizamos o comando dmesg. Esse comando realiza a leitura direta do Kernel Ring Buffer (anel de buffer do kernel), uma área especial de memória volátil que armazena uma quantidade massiva de mensagens geradas pelo núcleo do sistema operacional.

Estouro de Capacidade: Em sistemas altamente ativos ou que estejam enfrentando anomalias intermitentes de hardware e erros massivos, a capacidade física desse buffer pode ser excedida. Quando isso ocorre, as mensagens mais antigas são descartadas e perdidas para dar espaço aos novos registros. O tamanho limite desse buffer é determinado estritamente no momento em que o kernel é compilado, tornando sua alteração um processo complexo.

Isolando Eventos com dmesg e grep

A execução do comando dmesg isolado pode despejar até 512 kilobytes de linhas de texto ininterruptas no terminal. Por esse motivo, é altamente recomendável canalizar a sua saída por meio de um pipe para ferramentas de paginação ou filtragem como o less ou o grep.

Por exemplo, se um administrador estiver realizando o diagnóstico de problemas (troubleshooting) em um periférico ou barramento USB, filtrar a busca pelo termo **"usb"** otimiza drasticamente a análise. No exemplo abaixo, adicionamos o modificador -i no comando grep para que ele ignore a diferença entre letras maiúsculas e minúsculas (case-insensitive): 

sysadmin@localhost:~$ dmesg | grep -i usb
usbcore: registered new interface driver usbfs
usbcore: registered new interface driver hub
usbcore: registered new device driver usb
ehci_hcd: USB 2.0 'Enhanced' Host Controller (EHCI) Driver
ohci_hcd: USB 1.1 'Open' Host Controller (OHCI) Driver
ohci_hcd 0000:00:06.0: new USB bus registered, assigned bus number 1
usb usb1: New USB device found, idVendor=1d6b, idProduct=0001
usb usb1: New USB device strings: Mfr=3, Product=2, SerialNumber=1

13.6 Filesystem Hierarchy Standard (FHS)

Entre os padrões mantidos e apoiados pela Linux Foundation está o Filesystem Hierarchy Standard (FHS) (Padrão de Hierarquia do Sistema de Arquivos). Um padrão é um conjunto de regras ou diretrizes recomendadas para garantir a consistência de um ambiente. No entanto, essas diretrizes podem ser flexibilizadas ou modificadas, seja por decisões de design de uma distribuição específica ou por administradores em servidores isolados.

O FHS categoriza cada diretório do sistema operacional sob duas perspectivas cruzadas:

  • Compartilhável (Shareable) vs Não Compartilhável: Refere-se a se os dados do diretório podem ser compartilhados de forma segura através da rede com outras máquinas ou se devem ser estritamente locais.
  • Estático (Static) vs Variável: Define se os arquivos contidos no diretório permanecem inalterados sem intervenção administrativa (estáticos) ou se mudam constantemente durante a rotina do sistema (variáveis).

Matriz de Classificação FHS:

Classificação Não Compartilhável (Not Shareable) Compartilhável (Shareable)
Variável /var/lock (Arquivos de bloqueio local) /var/mail (Caixas de e-mail dos usuários)
Estático /etc (Configurações locais do host) /opt (Softwares de terceiros adicionais)

Diagrama Estrutural da Árvore de Diretórios (FHS)

Abaixo está representada a estrutura de níveis e dependências do sistema de arquivos Linux unificado a partir da raiz (/):

/ (Raíz do Sistema)
├── bin/ (Binários essenciais do sistema: ls, cp, rm)
├── boot/ (Arquivos de inicialização e Kernel Linux)
├── dev/ (Arquivos especiais de dispositivos de hardware)
├── etc/ (Arquivos de configuração do host local)
├── home/ (Diretórios pessoais dos usuários comuns)
├── lib/ (Bibliotecas compartilhadas essenciais para /bin e /sbin)
├── lib64/ (Bibliotecas essenciais para arquitetura 64-bits)
├── media/ (Ponto de montagem para mídias removíveis automáticas)
├── mnt/ (Ponto de montagem temporária manual)
├── opt/ (Pacotes de software adicionais de terceiros)
├── proc/ (Pseudo-sistema de arquivos com dados do kernel e processos)
├── root/ (Diretório pessoal do superusuário root)
├── sbin/ (Binários de administração do sistema essenciais)
├── srv/ (Dados de serviços específicos hospedados na máquina)
├── sys/ (Pseudo-sistema de arquivos com dados de hardware)
├── tmp/ (Arquivos temporários públicos limpos no boot)
├── usr/ (Segunda Hierarquia - Arquivos não-essenciais compartilhados)
└── local/ (Terceira Hierarquia - Programas instalados localmente/compilados)
└── bin/ , lib/ , sbin/ (Estrutura repetida localmente)
└── var/ (Quarta Hierarquia - Arquivos de dados altamente variáveis)
├── cache/ (Dados de cache de aplicações)
├── lock/ (Arquivos de travas de recursos compartilhados)
├── log/ (Arquivos de logs e auditorias do sistema)
└── spool/ (Filas de processamento, ex: impressão e e-mails)

Tabela Detalhada das Hierarquias FHS

O FHS divide o sistema operacional em quatro níveis hierárquicos principais de organização estrutural:

Diretório Raiz Escopo Técnico do Conteúdo Mapeado
/ A base absoluta da estrutura de arquivos. Unifica todos os diretórios locais, partições remotas, mídias externas e volumes de rede em uma árvore lógica única.
/bin Comandos essenciais e utilitários básicos de espaço de usuário executáveis por qualquer conta (ex: ls, cp, rm).
/boot Arquivos fundamentais para a carga inicial da máquina, incluindo o próprio Kernel Linux e os mapas do gerenciador de boot (GRUB).
/dev Arquivos lógicos que representam dispositivos de hardware (ex: discos, partições, terminais), além de arquivos virtuais especiais como /dev/null e /dev/zero.
/etc Centraliza os arquivos de configuração locais do host. Não contém binários executáveis.
/home Diretório de armazenamento e escopo pessoal dos usuários comuns do sistema operacional.
/lib Bibliotecas dinâmicas compartilhadas vitais para dar suporte aos binários encontrados em /bin e /sbin.
/lib64 Bibliotecas de suporte e links de execução construídos nativamente para arquiteturas x86 de 64 bits.
/media Diretório para montagem automática de mídias de armazenamento removíveis (como pendrives USB ou discos ópticos).
/mnt Ponto de ancoragem genérico e limpo para montagens temporárias de sistemas de arquivos realizadas manualmente pelo administrador.
/opt Destinado à instalação de pacotes de softwares proprietários ou aplicativos monolíticos de terceiros.
/proc Pseudo-sistema de arquivos que atua como uma interface de leitura volátil para o kernel expor dados sobre processos ativos e hardware.
/root O diretório pessoal e restrito pertencente exclusivamente ao superusuário administratrador (root).
/sbin Binários e utilitários de sistema essenciais focados estritamente nas tarefas de administração realizadas pelo usuário root (ex: fdisk, init).
/sys Pseudo-sistema de arquivos estruturado em memória RAM para expor parâmetros finos de barramentos e hardwares plugados no sistema.
/srv Armazena dados operacionais de serviços específicos providos por este servidor para a rede (como repositórios de arquivos ou dados web).
/tmp Espaço público onde qualquer processo ou usuário possui direito de gravação de arquivos temporários. É limpo de forma automática a cada boot.
/usr Segunda Hierarquia: Concentra os dados, programas e bibliotecas não-essenciais compartilhados para uso de múltiplos usuários. Pode ser montado em modo somente-leitura (read-only).
/usr/local Terceira Hierarquia: Reservado para a instalação local de softwares que não fazem parte do repositório oficial da distribuição (geralmente softwares compilados manualmente a partir do código-fonte).
/var Quarta Hierarquia: Centraliza arquivos cujos conteúdos mudam constantemente ao longo do tempo (logs, spoolers de impressão, caches de rede, tabelas dinâmicas).

Diretórios Essenciais vs Não-Essenciais no Boot

Enquanto o sistema de arquivos raiz (/) e as pastas do seu primeiro nível hierárquico são categorizados como **essenciais** (obrigatórios para inicializar o kernel e montar a base operacional), as estruturas em /var, /usr e /usr/local são classificadas como não-essenciais para a fase inicial de boot.

Ambientes de Resgate (Single-User Mode): Em cenários críticos de manutenção e recuperação de falhas (como inicializar a máquina no Modo de Usuário Único), o kernel disponibilizará apenas a hierarquia raiz estável no disco. Essa blindagem de design isola problemas em partições secundárias, garantindo que as ferramentas básicas de manutenção (mapeadas em /bin e /sbin) estejam sempre funcionais para o administrador sanar o erro.
