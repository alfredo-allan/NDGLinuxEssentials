Open Source Software and Licensing

Software de Código Aberto e Licenciamento

4.1 Introdução

Projetos de software assumem a forma de código-fonte, que é um conjunto legível de instruções de computador. Como o código-fonte não é entendido diretamente pelo computador, ele deve ser compilado em instruções de máquina por um compilador. O compilador é um programa especial que reúne todos os arquivos de código-fonte e gera instruções que podem ser executadas no computador, como pelo kernel Linux.

Historicamente, o software comercial tem sido vendido sob uma licença de código fechado (closed source), o que significa que os usuários têm o direito de usar o código de máquina, também conhecido como binário ou executável, mas não podem ver o código-fonte. Frequentemente, a licença afirma explicitamente que os usuários não podem tentar fazer engenharia reversa do código de máquina de volta para o código-fonte para descobrir o que ele faz.

Considere Isto: Código-fonte compilado em programas binários é um método de criar programas e executar instruções computacionais. Outro é os muitos tipos de linguagens interpretadas, como PERL, Python e até scripts BASH, onde o código não é compilado, mas alimentado para um programa interpretador, tipicamente um executável binário que entende e implementa as instruções contidas no código-fonte ou scripts.

O desenvolvimento do Linux acompanha de perto a ascensão do software de código aberto (open source). No início existia o shareware, programas disponíveis gratuitamente onde os usuários não tinham necessariamente acesso ao código-fonte. Havia muitas coisas boas nisso, mas também era problemático porque programas maliciosos podiam ser disfarçados como jogos inocentes, protetores de tela e utilitários.

O código aberto adota uma visão centrada no código-fonte. A filosofia do open source é que os usuários têm o direito de obter o código-fonte do software, e de expandir e modificar programas para seu próprio uso. Isso também significava que o código poderia ser inspecionado quanto a backdoors, vírus e spyware. Ao criar uma comunidade de desenvolvedores e usuários, a responsabilidade por bugs, vulnerabilidades de segurança e problemas de compatibilidade tornou-se uma responsabilidade compartilhada. Esta nova comunidade global de entusiastas de computadores foi impulsionada pela crescente disponibilidade de serviços de internet mais rápidos e da world wide web.

Existem muitas variantes diferentes de código aberto, mas todas concordam que os usuários devem ter acesso ao código-fonte. Onde elas diferem é em como se pode, ou se deve, redistribuir alterações.

O Linux adotou esta filosofia com grande sucesso. Como o Linux foi escrito na linguagem de programação C, e espelhava o design e a funcionalidade de sistemas UNIX já estabelecidos, tornou-se naturalmente um fórum onde as pessoas podiam desenvolver e compartilhar novas ideias. Livres das restrições de plataformas de hardware e software proprietárias, um grande número de programadores muito habilidosos pôde contribuir para as várias distribuições, resultando em software que é frequentemente mais robusto, estável, adaptável e, francamente, melhor do que as ofertas proprietárias e de código fechado que dominaram as décadas anteriores.

Grandes organizações estavam compreensivelmente suspeitas em usar software construído desta nova maneira, mas com o tempo perceberam que seus melhores programadores estavam trabalhando em projetos open source baseados em Linux em seu tempo livre. Logo, servidores Linux e programas open source começaram a superar os caros sistemas proprietários já existentes. Quando chegou a hora de atualizar hardware obsoleto, os mesmos programadores, engenheiros e administradores de sistema que começaram a trabalhar com Linux como hobby conseguiram convencer seus chefes a dar uma chance ao Linux. O resto é, como se diz, história.

Antes do desenvolvimento do Linux, muitas aplicações corporativas e científicas rodavam em sistemas UNIX proprietários. Empresas, universidades e governos que operam grandes fazendas de servidores gostavam da estabilidade e relativa facilidade de desenvolvimento de aplicações que estas plataformas ofereciam.

O UNIX foi inicialmente criado em 1969. Na sua quarta edição, em 1973, foi reescrito na linguagem de programação C que ainda é proeminente hoje. Em 1984, a Universidade da Califórnia Berkeley lançou o 4.2BSD que introduziu o TCP/IP, a especificação de rede que sustenta a Internet. No início dos anos 1990, quando o desenvolvimento do Linux começou, diferentes empresas desenvolvendo sistemas operacionais UNIX perceberam que seus sistemas precisavam ser compatíveis e começaram a trabalhar na especificação X/Open que ainda é usada hoje.

Ao longo dos anos, cientistas da computação e as organizações que os empregam perceberam o benefício de sistemas que fornecem ferramentas familiares e maneiras consistentes de realizar tarefas específicas. A padronização das interfaces de programação de aplicações (APIs) permite que programas escritos para um sistema operacional UNIX ou Linux específico sejam portados (convertidos) relativamente fácil para rodar em outro. Assim, embora sistemas UNIX proprietários ainda estejam em uso em todo o mundo em ambientes onde soluções "certificadas" são preferidas, a interoperabilidade destes sistemas juntamente com computadores Linux é valorizada pela indústria, academia e governos que os utilizam.

Importância dos Padrões: A importância das organizações de padrões não pode ser subestimada. Grupos como o IEEE (Institute of Electrical and Electronics Engineers) e POSIX (Portable Operating System Interface) permitem que profissionais de diferentes empresas e instituições colaborem em especificações que tornam possível que diferentes sistemas operacionais e programas trabalhem juntos.

Não importa se um programa é de código fechado ou aberto, simples ou complexo, se for escrito para esses padrões, outros poderão usá-lo e modificá-lo no futuro. Cada inovação na computação é construída sobre o trabalho de outros que vieram antes. O software de código aberto é uma colaboração de diferentes pessoas com diferentes necessidades e origens, todos trabalhando juntos para fazer algo melhor do que qualquer um deles poderia ter feito individualmente. Os padrões são o que tornam isso possível, e as muitas organizações que os criam, mantêm e promovem são integrais para a indústria.

4.2 Licenciamento de Código Aberto

Ao falar sobre compra de software, existem três componentes distintos:

  • Propriedade (Ownership) – Quem possui a propriedade intelectual por trás do software?
  • Transferência de Dinheiro – Como o dinheiro muda de mãos, se é que muda?
  • Licenciamento (Licensing) – O que você recebe? O que você pode fazer com o software? Pode usá-lo em apenas um computador? Pode dar para outra pessoa?

Na maioria dos casos, a propriedade do software permanece com a pessoa ou empresa que o criou. Os usuários recebem apenas uma licença para usar o software; isso é uma questão de lei de direitos autorais. A transferência de dinheiro depende do modelo de negócios do criador. É o licenciamento que diferencia o software de código aberto do software de código fechado.

Dois exemplos contrastantes ajudarão a começar:

Com o Microsoft Windows, a Microsoft Corporation possui a propriedade intelectual. A licença em si, o End User License Agreement (EULA), é um documento legal personalizado que você deve clicar, indicando sua aceitação, para instalar o software. A Microsoft mantém o código-fonte e distribui apenas cópias binárias através de canais autorizados. Para a maioria dos produtos de consumo, você pode instalar o software em um computador e não pode fazer cópias do disco, exceto para backup. Você não pode fazer engenharia reversa do software. Você paga por uma cópia do software, que lhe dá atualizações menores, mas não atualizações principais.

O Linux é propriedade de Linus Torvalds. Ele colocou o código sob uma licença chamada GNU General Public License version 2 (GPLv2). Esta licença, entre outras coisas, diz que o código-fonte deve ser disponibilizado a qualquer pessoa que pedir e que qualquer pessoa pode fazer alterações. Uma ressalva é que se alguém fizer alterações e as distribuir, deve colocar as alterações sob a mesma licença para que outros possam se beneficiar. A GPLv2 também diz que ninguém pode cobrar pela distribuição do código-fonte, exceto pelos custos reais de fazê-lo (como copiá-lo para mídia removível).

Em geral, quando alguém cria algo, também adquire o direito de decidir como será usado e distribuído. Software Livre e de Código Aberto (FOSS - Free and Open Source Software) refere-se a software onde este direito foi cedido; qualquer pessoa pode visualizar o código-fonte e redistribuí-lo. Linus Torvalds fez isso com o Linux – mesmo tendo criado o Linux, ele não pode proibir alguém de usá-lo em seu computador porque cedeu esse direito através da licença GPLv2.

Software Livre vs Código Aberto: Embora frequentemente usados como sinônimos, há uma diferença sutil. "Software Livre" (Free Software) enfatiza liberdades éticas, enquanto "Código Aberto" (Open Source) foca nos benefícios práticos do desenvolvimento colaborativo. Ambos compartilham o princípio do acesso ao código-fonte.

O licenciamento de software é uma questão política, portanto não é surpresa que existam muitas opiniões diferentes. Organizações criaram suas próprias licenças que incorporam suas visões particulares, então é mais fácil escolher uma licença existente do que criar a sua própria. Por exemplo, universidades como o Massachusetts Institute of Technology (MIT) e a University of California criaram licenças, assim como projetos como a Apache Foundation. Além disso, grupos como a Free Software Foundation criaram suas próprias licenças para promover sua agenda.

Principais Licenças Open Source:
  • GPL (GNU General Public License) – Copyleft forte: modificações devem ser compartilhadas sob a mesma licença
  • MIT License – Permissiva: permite uso proprietário, apenas requer atribuição
  • Apache License 2.0 – Permissiva com patentes e atribuição
  • BSD License – Permissiva, variações (2-cláusula, 3-cláusula)
  • LGPL (Lesser GPL) – Permite vinculação com código proprietário

MIT Permissiva Apenas atribuição exigida React, Node.js, jQuery

Copyleft: Um conceito fundamental da GPL. Enquanto o copyright tradicional restringe cópia e modificação, o copyleft usa a lei de direitos autorais para garantir que as liberdades do software sejam preservadas em todas as versões modificadas ou estendidas.

4.2.1 A Free Software Foundation (FSF)

Dois grupos podem ser considerados as forças mais influentes no mundo do código aberto: a Free Software Foundation (FSF) e a Open Source Initiative (OSI).

Apenas alguns anos após o desenvolvimento do projeto GNU, Richard Stallman fundou a Free Software Foundation (FSF) em 1985 com o objetivo de promover o software livre. Neste contexto, a palavra "livre" (free) não se refere ao preço, mas à liberdade de compartilhar, estudar e modificar o código-fonte subjacente. De acordo com seu site, a FSF acredita que os usuários devem ter "controle sobre a tecnologia que usamos em nossas casas, escolas e empresas".

A FSF também defende que as licenças de software devem impor a abertura das modificações. É sua visão que se alguém modifica software livre, deve ser obrigado a compartilhar quaisquer alterações feitas quando as compartilhar novamente. Esta filosofia específica é chamada de copyleft. Segundo a FSF, "copyleft é um método geral para tornar um programa (ou outro trabalho) livre (no sentido de liberdade, não "preço zero"), e exigir que todas as versões modificadas e estendidas do programa também sejam livres".

A FSF também defende contra patentes de software e atua como um cão de guarda para organizações de padrões, manifestando-se quando um padrão proposto pode violar os princípios do software livre ao incluir itens como Digital Rights Management (DRM), que restringem o que pode ser feito com programas compatíveis.

A FSF desenvolveu seu próprio conjunto de licenças que são gratuitas para qualquer um usar, baseadas na GNU General Public License (GPL) original. A FSF mantém atualmente:

  • GNU General Public License version 2 (GPLv2)
  • GNU General Public License version 3 (GPLv3)
  • GNU Lesser General Public License version 2 (LGPLv2)
  • GNU Lesser General Public License version 3 (LGPLv3)

Estas licenças são destinadas a serem incluídas no código-fonte real para garantir que todas as futuras variantes e modificações do programa original continuem a ter a mesma liberdade de uso que o original. A licença GPL e suas variantes são ferramentas legais poderosas para avançar a causa do software livre em todo o mundo. O que começou em 1983 como o desejo de um homem de compartilhar e melhorar software, permitindo que outros o modificassem, acabou mudando o mundo.

Considere Isto: As mudanças entre GPLv2 e GPLv3 focaram-se amplamente no uso de software livre em um dispositivo de hardware fechado, o que foi chamado de Tivoization. TiVo é uma empresa que construiu um gravador de vídeo digital de televisão em seu próprio hardware e usou Linux como base para seu software. Embora a TiVo tenha lançado o código-fonte de sua versão do Linux conforme exigido pela GPLv2, o hardware não executava binários modificados. Aos olhos da FSF, isso ia contra o espírito da GPLv2, então eles adicionaram uma cláusula específica à versão 3 da licença. Linus Torvalds concorda com a TiVo nesta questão e optou por permanecer com a GPLv2.
Resumo da Filosofia FSF:
  • Liberdade 0: Executar o programa como desejar
  • Liberdade 1: Estudar e modificar o código-fonte
  • Liberdade 2: Redistribuir cópias
  • Liberdade 3: Distribuir cópias de suas versões modificadas
Licença Ano Característica Principal Diferença da anterior
GPLv2 1991 Copyleft básico Licença original do Linux kernel
GPLv3 2007 Anti-Tivoization Proíbe restrições de hardware em software modificado
LGPLv2 / v3 1991 / 2007 Permite vinculação com código proprietário Mais permissiva que a GPL

4.2.2 A Open Source Initiative (OSI)

A Open Source Initiative (OSI) foi fundada em 1998 por Bruce Perens e Eric Raymond. Eles acreditavam que a Free Software Foundation era politicamente carregada demais e que licenças menos extremas eram necessárias, particularmente em relação aos aspectos de copyleft das licenças da FSF.

A OSI acredita que não apenas o código-fonte deve estar livremente disponível, mas também que nenhuma restrição deve ser colocada no uso do software, independentemente do uso pretendido. Ao contrário da FSF, a OSI não possui seu próprio conjunto de licenças. Em vez disso, a OSI tem um conjunto de princípios e adiciona licenças a essa lista se elas atenderem a esses princípios, chamadas de licenças de código aberto (open source licenses). Software que está em conformidade com uma licença de código aberto é, portanto, software de código aberto.

Um tipo de licença de código aberto é a BSD (Berkeley Software Distribution) e seus derivados, que são muito mais simples que a GPL. Atualmente existem duas licenças "BSD" aprovadas pela OSI: a 2-Cláusula e a 3-Cláusula. Estas licenças afirmam que você pode redistribuir o código-fonte e os binários, desde que mantenha os avisos de direitos autorais e não implique que o criador original endossa sua versão.

Resumo da Licença BSD: "Faça o que quiser com este software, apenas não diga que você o escreveu."

Segundo a FSF, a licença BSD original tinha uma falha grave: exigia que os desenvolvedores adicionassem uma cláusula reconhecendo a Universidade da Califórnia, Berkeley em cada anúncio de software licenciado desta forma. Como outros copiaram esta licença simples, eles incluíram reconhecimento para suas próprias instituições, o que levou a mais de 75 desses reconhecimentos em alguns casos.

As licenças da FSF, como a GPLv2, também são licenças de código aberto. No entanto, muitas licenças de código aberto, como BSD e MIT, não contêm as disposições de copyleft e, portanto, não são aceitáveis para a FSF. Estas licenças são chamadas de licenças de software livre permissivas porque são permissivas em como você pode redistribuir o software. Você pode pegar software licenciado sob BSD e incluí-lo em um produto de software fechado, desde que dê a devida atribuição.

Em vez de se debruçar sobre os pontos mais sutis de Código Aberto e Software Livre, a comunidade começou a se referir a eles coletivamente como Free and Open Source Software (FOSS) – Software Livre e de Código Aberto.

A palavra inglesa "free" pode significar "grátis" (como em "free lunch" – almoço grátis) ou "livre" (como em "free speech" – liberdade de expressão). Esta ambiguidade levou à inclusão da palavra "libre" (do espanhol/francês) para se referir à segunda definição. Assim, chegamos ao termo Free/Libre/Open Source Software (FLOSS).

Comparação: FSF vs OSI
  • FSF (Free Software Foundation): Foco ético e político, defende copyleft (GPL)
  • OSI (Open Source Initiative): Foco prático e comercial, aceita licenças permissivas (BSD, MIT)

FLOSS: O acrônimo Free/Libre/Open Source Software é usado para unificar os dois movimentos, reconhecendo que ambos compartilham o mesmo objetivo fundamental – tornar o código-fonte acessível – mesmo que por diferentes razões filosóficas.

4.2.3 Creative Commons (CC)

As licenças FOSS são principalmente relacionadas a software. Pessoas colocaram obras como desenhos e planos sob licenças FOSS, mas esse não era o objetivo pretendido.

Quando o software é colocado em domínio público (public domain), o autor renunciou a todos os direitos, incluindo os direitos autorais sobre a obra. Em alguns países, este é o padrão quando o trabalho é feito por uma agência governamental. Em alguns países, o trabalho protegido por direitos autorais se torna domínio público após a morte do autor e um longo período de espera.

A organização Creative Commons (CC) criou as Licenças Creative Commons que tentam abordar as intenções por trás das licenças FOSS para entidades não relacionadas a software. As licenças CC também podem ser usadas para restringir o uso comercial, se esse for o desejo do detentor dos direitos autorais.

As licenças CC são compostas pelo seguinte conjunto de condições que o criador pode aplicar à sua obra:

  • Attribution (BY) – Todas as licenças CC exigem que o criador receba crédito, sem implicar que o criador endossa o uso.
  • ShareAlike (SA) – Permite que outros copiem, distribuam, executem e modifiquem a obra, desde que o façam sob os mesmos termos.
  • NonCommercial (NC) – Permite que outros distribuam, exibam, executem e modifiquem a obra para qualquer propósito que não seja comercial.
  • NoDerivatives (ND) – Permite que outros distribuam, exibam e executem apenas cópias originais da obra. Eles devem obter permissão do criador para modificá-la.
Combinações: Estas condições são então combinadas para criar as seis principais licenças oferecidas pelo Creative Commons.

1. Attribution (CC BY)

Muito parecida com a licença BSD, você pode usar conteúdo CC BY para qualquer uso, mas deve creditar o detentor dos direitos autorais.

2. Attribution ShareAlike (CC BY-SA)

Uma versão copyleft da licença Attribution. Obras derivadas devem ser compartilhadas sob a mesma licença, muito parecido com os ideais do Software Livre.

3. Attribution NoDerivs (CC BY-ND)

Você pode redistribuir o conteúdo sob as mesmas condições do CC-BY, mas não pode alterá-lo.

4. Attribution-NonCommercial (CC BY-NC)

Assim como CC BY, mas você não pode usá-lo para fins comerciais.

5. Attribution-NonCommercial-ShareAlike (CC BY-NC-SA)

Baseia-se na licença CC BY-NC, mas exige que suas alterações sejam compartilhadas sob a mesma licença.

6. Attribution-NonCommercial-NoDerivs (CC BY-NC-ND)

Você está compartilhando o conteúdo para ser usado para fins não comerciais, mas as pessoas não podem alterar o conteúdo.

7. No Rights Reserved (CC0)

Esta é a versão Creative Commons de domínio público. O criador renuncia a todos os direitos sobre a obra.

4.3 Modelos de Negócio em Código Aberto

Se todo este software é gratuito, como alguém pode ganhar dinheiro com ele?

Primeiro, você deve entender que não há nada na GPL que proíba a venda de software. Na verdade, o direito de vender software faz parte da licença GPL. Novamente, lembre-se de que a palavra "free" se refere à liberdade, não ao preço. Empresas que agregam valor a esses programas gratuitos são encorajadas a ganhar o máximo de dinheiro possível e reinvestir esses lucros no desenvolvimento de mais e melhores softwares.

1. Suporte e Garantia

Uma das maneiras mais simples de ganhar dinheiro é vender suporte ou garantia em torno do software. Empresas como Canonical (desenvolvedora do Ubuntu) e Red Hat se tornaram grandes empresas ao criar distribuições Linux e ferramentas que permitem que usuários comerciais gerenciem suas empresas e ofereçam produtos e serviços a seus clientes.

Exemplo de Sucesso: A Red Hat, pioneira no modelo de suporte para Linux, foi adquirida pela IBM em 2019 por aproximadamente US$ 34 bilhões – a maior aquisição de software da história.

2. Projetos que Viram Empresas

Muitos outros projetos de código aberto também se expandiram para negócios substanciais. Na década de 1990, Gerald Combs trabalhava em um provedor de serviços de Internet e começou a escrever sua própria ferramenta de análise de rede porque as ferramentas similares da época eram caras. Mais de 600 pessoas já contribuíram para o projeto, chamado Wireshark. Hoje é frequentemente considerado melhor do que as ofertas comerciais e levou à formação de uma empresa para vender produtos e suporte. Como muitas outras, esta empresa foi comprada por uma empresa maior que apoia seu desenvolvimento contínuo.

3. Hardware e Software Embutido

Empresas como TiVo empacotam hardware ou adicionam software de código fechado extra para vender junto com o software livre. Aparelhos e sistemas embarcados que usam Linux são um negócio de bilhões de dólares e abrangem desde DVRs domésticos até câmeras de segurança e dispositivos de fitness vestíveis. Muitos firewalls de consumo e dispositivos de entretenimento seguem este modelo.

4. Contribuição Corporativa

Hoje, tanto empregadores grandes quanto pequenos têm indivíduos e, às vezes, grupos inteiros dedicados a trabalhar em projetos de código aberto. Empresas de tecnologia competem pela oportunidade de influenciar projetos que moldarão o futuro de seus setores. Outras empresas dedicam recursos a projetos que precisam para uso interno. À medida que mais negócios são realizados em recursos de nuvem, a oportunidade para programadores de código aberto continua a se expandir.

Modelo de Negócio Como Funciona Exemplo
Suporte Corporativo Venda de suporte técnico, garantia e consultoria Red Hat, Canonical (Ubuntu)
Open Core Versão básica gratuita, recursos avançados pagos GitLab, Elastic, MySQL (Oracle)
Hardware + Software Vende hardware que roda software livre TiVo, roteadores, dispositivos IoT
Serviços em Nuvem Oferece software como serviço (SaaS) WordPress.com, GitLab.com
Doações / Patrocínio Financiamento por doações e patrocinadores Wikimedia, Mozilla, Blender
Dual Licensing Duas licenças: GPL para código aberto, comercial para proprietário MySQL (Oracle), Qt

Principais Takeaways:
  • 💰 Código aberto NÃO significa sem dinheiro – apenas que o código é livre
  • 📦 Valor está nos serviços (suporte, garantia, treinamento, certificação)
  • 🏢 Empresas lucram com open source – Red Hat, Canonical, Databricks, Elastic
  • 🔓 Open core é um modelo popular: base gratuita, recursos premium pagos
  • ☁️ Nuvem abriu novas oportunidades para projetos open source
Desafio do Open Source: O maior desafio para empresas open source é equilibrar a transparência e liberdade do código aberto com a necessidade de gerar receita sustentável. Muitas empresas falham ao tornar sua versão "open core" muito limitada ou ao mudar licenças de forma controversa (ex: Elastic, HashiCorp).
