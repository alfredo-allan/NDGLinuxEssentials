Módulo 18

Diretórios e Arquivos Especiais

Dominando permissões especiais no Linux: os mecanismos ocultos de segurança do SetUID, SetGID e Sticky Bit.

18.1 Introdução

Na grande maioria das circunstâncias operacionais, os conjuntos de permissões básicos e tradicionais do Linux — Leitura (read), Escrita (write) e Execução (execute) — mostram-se perfeitamente suficientes para suprir as demandas rotineiras de isolamento e segurança de usuários individuais ou de grupos em uma organização.

Contudo, quando múltiplos usuários precisam colaborar de maneira integrada, simultânea e contínua sobre os mesmos arquivos e estruturas de diretórios, esse modelo básico baseado puramente em DAC (Discretionary Access Control) pode apresentar limitações severas de consistência e governança de dados.

Para sanar essas restrições arquiteturais, o Linux disponibiliza o conjunto de **Permissões Especiais**: os bits **SetUID (suid)**, **SetGID (sgid)** e o **Sticky Bit**. Eles foram especificamente projetados para flexibilizar o controle de processos, herança de propriedades e proteção de exclusão sem comprometer a segurança global do sistema de arquivos.

18.2 O Bit SetUID (suid)

Quando a permissão especial SetUID (Set User ID) é configurada em um arquivo binário executável (um programa compilado), o processo resultante é executado com os privilégios do **usuário proprietário (dono) do arquivo**, e não com os privilégios do usuário comum que disparou o comando no terminal.

Essa permissão é aplicada cirurgicamente em um punhado de utilitários cruciais do sistema para que contas comuns possam realizar tarefas administrativas específicas de forma controlada, garantindo acesso temporário a arquivos confidenciais que, em situações normais, seriam totalmente inacessíveis.

O Dilema do Acesso a Arquivos Sensíveis

Para compreender o papel do SetUID, considere o cenário abaixo, onde o usuário comum sysadmin tenta inspecionar o arquivo restrito /etc/shadow (que armazena os hashes das senhas do sistema): 

sysadmin@localhost:~$ more /etc/shadow
/etc/shadow: Permission denied
sysadmin@localhost:~$ ls -l /etc/shadow
-rw-r-----. 1 root root 5195 Oct 21 19:57 /etc/shadow

Os bits de acesso do /etc/shadow barram qualquer tentativa de leitura ou gravação por contas convencionais. Como ele pertence ao usuário root e ao grupo root, apenas o superusuário administrador possui autoridade nativa sobre ele.

Agora reflita sobre o comando passwd, utilizado para alterar senhas. Quando um usuário comum roda o passwd para redefinir sua credencial, o programa altera com sucesso a sua respectiva linha lá dentro do /etc/shadow.

Como isso é possível se qualquer outro utilitário disparado pelo sysadmin recebe um erro de permissão negada?

O Segredo Operacional: A mágica ocorre porque o binário do comando passwd possui o bit **SetUID ativo**. No momento em que o processo do passwd solicita acesso de gravação ao arquivo /etc/shadow, o kernel do Linux eleva temporariamente as credenciais da tarefa, agindo como se quem estivesse manipulando o arquivo fosse o próprio dono do binário (o usuário root), e ignorando as restrições da conta do usuário que iniciou a execução.

Identificando o Bit na Listagem Longa

Você pode auditar a presença desta permissão especial inspecionando os metadados do binário com o comando ls -l: 

sysadmin@localhost:~$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 31768 Jan 28 2010 /usr/bin/passwd

Observe atentamente a string de permissões do output anterior: o bit SetUID é representado pela letra s localizada na terceira posição do bloco do dono (User), exatamente onde o caractere de execução tradicional (x) costuma ficar.

  • Uma letra s minúscula sinaliza que **ambos** os bits estão ativos: o SetUID e o direito de execução (x).
  • Uma letra S maiúscula sinaliza um cenário anômalo: o bit SetUID está ativo, mas o usuário **não** possui a permissão básica de execução para aquele arquivo.

Manipulação Prática via comando chmod

Assim como as permissões tradicionais, o bit SetUID pode ser gerenciado utilizando tanto a técnica simbólica quanto a numérica (octal).

Método Simbólico:

Para adicionar o bit SetUID simbolicamente à classe do usuário, combine o modificador u e o operador +s: 

chmod u+s nome_do_arquivo

Para remover o bit SetUID mantendo os outros privilégios intactos, utilize o operador -s:

chmod u-s nome_do_arquivo

Método Numérico (Octal):

Na técnica octal, as permissões especiais passam a utilizar um prefixo de **quatro dígitos**. O bit SetUID possui um peso fixo de 4000.

Para ativar a propriedade em um arquivo cujos bits básicos atuais sejam 775, somamos o valor especial para gerar o argumento 4775: 

chmod 4775 nome_do_arquivo

Para limpar a permissão especial mantendo os bits básicos originais, basta redefinir o primeiro dígito da máscara como zero: 

chmod 0775 nome_do_arquivo
Atenção à Sobrescrita Involuntária em Máscaras Octais: Nos capítulos anteriores, alteramos privilégios usando máscaras padronizadas de três dígitos (como chmod 755). Quando essa abordagem simplificada é usada, o comando chmod assume automaticamente que o dígito de controle especial omitido equivale a 0.

Portanto, se você rodar uma máscara de apenas três posições sobre um arquivo que possua o SetUID (ou qualquer outro bit especial) configurado anteriormente, o sistema apagará e removerá a permissão especial de forma definitiva, restaurando o comportamento básico do arquivo.

18.3 O Bit SetGID (sgid)

A permissão especial SetGID (Set Group ID) possui uma arquitetura conceitualmente semelhante à do SetUID, porém seus mecanismos de controle atuam diretamente sobre as credenciais do grupo proprietário do objeto.

No ecossistema Linux, a aplicação do bit SetGID se ramifica em duas vertentes operacionais distintas, apresentando comportamentos completamente diferentes dependendo do elemento onde ele é injetado:

  • SetGID em Arquivos Executáveis: Altera as credenciais de grupo do processo em tempo de execução, agindo de forma análoga ao SetUID de usuário.
  • SetGID em Diretórios (Pastas): Altera as regras de herança e governança do sistema de arquivos para otimizar o trabalho colaborativo e o compartilhamento de dados.
O que observar a seguir: Nos próximos tópicos do módulo, iremos desmembrar e detalhar isoladamente as regras de funcionamento e os impactos práticos de cada um desses dois comportamentos do SetGID.

18.3.1 SetGID em Arquivos Executáveis

A permissão SetGID aplicada a um arquivo regular funciona de maneira análoga ao SetUID de usuário: ela permite que uma conta execute um binário de forma que o processo herde temporariamente os direitos de acesso do grupo proprietário do arquivo, e não do grupo principal do usuário que invocou o comando.

Enquanto o programa estiver em execução na memória, o kernel do Linux considera, para fins de validação de privilégios, que o processo pertence de fato ao respectivo grupo dono do binário.

O Caso Prático do Comando wall

Um excelente exemplo de uso prático do bit SetGID em arquivos executáveis é o comando /usr/bin/wall (utilizado para enviar mensagens globais de broadcast para os terminais de todos os usuários logados). Veja a listagem de metadados deste binário: 

sysadmin@localhost:~$ ls -l /usr/bin/wall
-rwxr-sr-x 1 root tty 30800 May 16  2018 /usr/bin/wall

A identificação do SetGID segue o mesmo padrão visual do SetUID, mas localiza-se na posição do bit de execução da classe do Grupo (Group) através de um caractere s minúsculo.

Como o arquivo pertence ao grupo tty e possui o SetGID ativo, qualquer usuário comum que rodar este programa assumirá temporariamente as prerrogativas do grupo tty em nível de kernel.

Por que este privilégio especial é necessário?

O comando wall precisa enviar dados brutos diretamente para as telas dos terminais ativos. No Linux, esses terminais são mapeados como arquivos de caracteres dentro de /dev/. Vamos checar os privilégios desses arquivos especiais: 

sysadmin@localhost:~$ ls -l /dev/tty?
crw--w----. 1 root tty  4, 0 Mar 29  2013 /dev/tty0
crw--w----. 1 root tty  4, 1 Oct 21 19:57 /dev/tty1

Analisando as permissões das entradas de terminal de hardware acima, percebe-se que o grupo proprietário tty possui permissão de escrita ativa (-w-), enquanto a classe dos usuários terceiros (others) possui zero privilégios de acesso (---).

Dessa forma, caso o bit SetGID fosse desativado do binário do wall, um usuário comum falharia imediatamente ao tentar emitir o alerta global, pois seu processo seria bloqueado pelo kernel por falta de permissões explícitas de gravação sobre os dispositivos de destino.

18.3.2 SetGID em Diretórios (Pastas)

Quando configurado em um diretório, o bit SetGID altera completamente a lógica padrão de atribuição de propriedades do Linux. Com ele ativo, qualquer arquivo ou subdiretório criado ali dentro herdará automaticamente o grupo proprietário da pasta pai.

Esse comportamento diverge da regra tradicional do sistema operacional, onde novos arquivos recebem, por padrão, o grupo principal (primário) do usuário que os criou.

Além disso, qualquer subdiretório criado dentro de uma pasta com SetGID não apenas herdará o grupo proprietário, mas também **receberá a ativação automática do bit SetGID em seus próprios metadados**. Em outras palavras, a propriedade SetGID propaga-se de forma hereditária por toda a árvore de subpastas subsequentes.

Auditando o Bit em Diretórios

Por padrão, rodar o comando ls em uma pasta lista os arquivos internos. Para inspecionar os metadados do próprio diretório alvo, precisamos adicionar a flag -d. Combinada com o -l (ls -ld), podemos checar a presença do SetGID: 

sysadmin@localhost:~$ ls -ld /tmp/data
drwxrwsrwx. 2 root demo 4096 Oct 30 23:20 /tmp/data

Na listagem longa, o SetGID é representado por um caractere s na posição de execução da classe do grupo:

  • Um s minúsculo indica que **ambos** os bits estão ativos: o SetGID e a permissão básica de execução para o grupo (x).
  • Um S maiúsculo indica que o SetGID está ativado, mas o grupo **não possui** a permissão básica de execução. Nesse estado, o SetGID fica inoperante (sem efeito prático), pois os membros do grupo não conseguirão sequer acessar ou transitar pelo diretório. Veja o exemplo abaixo: 
drwxrwSr-x. 2 root root 5036 Oct 30 23:22 /tmp/data2

Funcionamento Prático do Mecanismo

Considere as credenciais do usuário logado na sessão: seu grupo primário é sysadmin:

sysadmin@localhost:~$ id
uid=500(sysadmin) gid=500(sysadmin) groups=500(sysadmin),10001(research),10002(development)

Se este usuário gerar um arquivo em uma pasta comum, o grupo dono do arquivo será sysadmin. No entanto, se ele criar o arquivo dentro do diretório /tmp/data (que pertence ao grupo demo e possui SetGID), veja o que ocorre: 

sysadmin@localhost:~$ touch /tmp/data/file.txt
sysadmin@localhost:~$ ls -ld /tmp/data/file.txt
-rw-rw-r--. 1 sysadmin demo 0 Oct 30 23:21 /tmp/data/file.txt

O arquivo foi registrado associado ao grupo demo automaticamente.

Caso de Uso: O Problema dos Ambientes Compartilhados

Por que um administrador de sistemas configuraria uma pasta com SetGID? Imagine o seguinte cenário de colaboração entre setores:

👤 bob: Grupo payroll 👤 sue: Grupo staff 👤 tim: Grupo acct

Esses três usuários precisam trabalhar juntos em um projeto compartilhado. Para atendê-los, o administrador realiza os seguintes passos profissionais:

  1. Cria um novo grupo no sistema chamado team.
  2. Adiciona os usuários bob, sue e tim como membros secundários desse grupo.
  3. Cria a pasta /home/team e define seu grupo proprietário como team.
  4. Aplica a permissão rwxrwx--- (770) na pasta, isolando-a do resto do sistema.

O Problema Logístico (Sem SetGID):

Quando o usuário bob cria um documento na pasta do projeto, o arquivo nasce com o grupo padrão dele:

-rw-r-----. 1 bob payroll 100 Oct 30 23:21 /home/team/file.txt

Como sue e tim não fazem parte do grupo payroll, eles caem na classe others (---) desse arquivo. Consequentemente, eles ficam totalmente impedidos de ler, editar ou colaborar no arquivo criado pelo próprio colega de equipe.

A Solução Definitiva (Com SetGID):

Se o administrador aplicar o bit SetGID no diretório pai /home/team, no momento em que bob gerar um arquivo lá dentro, o arquivo assumirá o grupo da pasta: 

-rw-r-----. 1 bob team 100 Oct 30 23:21 /home/team/file.txt

A partir desse instante, sue e tim terão acesso imediato e garantido ao arquivo através dos privilégios concedidos à classe de grupo (r--), viabilizando a colaboração uniforme e sem fricção na equipe.

Sintaxe de Ativação

Para aplicar o bit SetGID em um diretório de forma simbólica, execute:

chmod g+s /nome_do_diretorio

Na metodologia de quatro dígitos numéricos (octal), o bit SetGID possui peso equivalente a 2000:

chmod 2770 /nome_do_diretorio

18.3.3 Configurando a Permissão SetGID

A manipulação do bit SetGID segue exatamente os mesmos princípios metodológicos do comando chmod vistos anteriormente. Podemos gerenciá-lo tanto através de argumentos literais (método simbólico) quanto por somas binárias (método numérico/octal).

Aplicação Prática da Sintaxe

Método Simbólico:

Para adicionar a permissão SetGID de forma simbólica a um arquivo ou diretório, utilize a classe do grupo (g) com o operador de adição (+s): 

chmod g+s <arquivo|diretorio>

Para remover a permissão SetGID mantendo os outros privilégios intactos, utilize o operador de subtração (-s):

chmod g-s <arquivo|diretorio>

Método Numérico (Octal):

Na técnica octal de quatro dígitos, o bit SetGID possui um peso de representação equivalente a 2000. Para ativá-lo, basta somar este valor aos bits já existentes do elemento.

Exemplo: Assumindo que um diretório possua originalmente os privilégios básicos configurados como 775, a incorporação do SetGID resultará na máscara 2775: 

chmod 2775 <arquivo|diretorio>

Para efetuar a remoção por vias numéricas, basta subtrair os 2000 pontos, definindo o primeiro dígito de controle especial como zero: 

chmod 0775 <arquivo|diretorio>
Lembrete de Sobrescrita: Assim como ocorre com o SetUID, a execução de um comando chmod utilizando apenas três dígitos octais (como chmod 755) assumirá o primeiro dígito oculto como 0, limpando e removendo qualquer bit SetGID previamente existente no arquivo ou pasta.

18.4 O Sticky Bit

A permissão especial Sticky Bit é utilizada para proteger a integridade de arquivos em diretórios compartilhados, impedindo que usuários apaguem ou renomeiem arquivos que não sejam de sua propriedade legítima.

Lembre-se do que foi estudado no Módulo 17: por padrão, qualquer usuário com permissão de Escrita (w) em um diretório pode criar elementos ali dentro e também deletar qualquer arquivo contido na pasta, mesmo que esse arquivo pertença a outra pessoa!

O Sticky Bit resolve esse problema de concorrência e segurança. Ele altera o comportamento da permissão de escrita do diretório para que a criação e exclusão geral de arquivos continuem ativas, mas com uma restrição crucial: os arquivos só podem ser deletados ou renomeados pelo proprietário real do arquivo ou pelo superusuário root.

Ambientes de Uso Comum: Os Diretórios Temporários

O melhor exemplo prático de aplicação do Sticky Bit no Linux são os diretórios /tmp e /var/tmp. Essas pastas foram projetadas pelo sistema operacional como áreas de rascunho globais, onde qualquer usuário ou processo em execução pode gerar um arquivo temporário.

Como essas pastas precisam ser obrigatoriamente graváveis por todos (permissão de escrita para a classe others), elas utilizam nativamente o Sticky Bit. Sem essa permissão especial, um usuário comum mal-intencionado ou um script mal configurado seria capaz de apagar bases de dados e arquivos vitais de outros usuários que estivessem processando dados naquele momento.

Identificando o Bit na Listagem Longa

O comando ls -l exibe a presença do Sticky Bit através do caractere t posicionado exatamente na última posição da string (no bit de execução da classe others): 

sysadmin@localhost:~$ ls -ld /tmp
drwxrwxrwst 1 root root 4096 Mar 14  2016 /tmp

O kernel adota duas representações textuais baseadas na caixa da letra:

  • Um t minúsculo indica que **ambos** os bits estão ativos: o Sticky Bit e a permissão básica de execução para terceiros (x).
  • Um T maiúsculo indica que apenas o Sticky Bit está configurado, enquanto o direito básico de execução para others está ausente.

Nota de Arquitetura: Enquanto um S maiúsculo indica uma inconsistência funcional no SetUID ou SetGID, o T maiúsculo não representa necessariamente um problema operacional para o Sticky Bit, desde que a classe do grupo dono ou do usuário dono ainda retenha as permissões de execução necessárias para acessar o diretório.

Sintaxe de Gerenciamento

Assim como os demais bits especiais, o Sticky Bit aceita ambas as metodologias de configuração do comando chmod:

Método Simbólico:

Para adicionar o Sticky Bit simbolicamente a uma pasta, utilize a classe outros (o) associada ao operador +t: 

chmod o+t <diretorio>

Para remover o bit de forma simbólica, utilize o operador -t:

chmod o-t <diretorio>

Método Numérico (Octal):

Na tabela de quatro dígitos octais, o Sticky Bit possui o peso representativo de 1000.

Exemplo: Se um diretório possui atualmente as permissões básicas definidas como 775, a incorporação do Sticky Bit gerará a máscara numérica 1775: 

chmod 1775 <diretorio>

Para remover o bit numericamente, basta limpar a casa milhar definindo o primeiro dígito de controle especial como zero:

chmod 0775 <diretorio>

18.5 Introdução a Links no Linux

Considere um cenário corporativo real onde um arquivo de configuração ou relatório vital esteja profundamente aninhado e enterrado dentro da árvore de diretórios do sistema, sob o seguinte caminho estrutural: 

/usr/share/doc/superbigsoftwarepackage/data/2013/october/tenth/valuable-information.txt

Imagine que outro usuário ou serviço do sistema atualize rotineiramente o conteúdo desse arquivo, e você precise acessá-lo ou inspecioná-lo de forma regular e frequente. Digitar esse caminho absoluto gigantesco toda vez que precisar interagir com o elemento não é, de forma alguma, uma escolha ideal ou produtiva para o seu fluxo de trabalho.

Contudo, o arquivo precisa obrigatoriamente residir e ser mantido exatamente nessa localização de origem para que a aplicação principal continue funcionando. Como o arquivo sofre alterações constantes em tempo real, você também **não pode simplesmente fazer uma cópia estática** dele para a sua pasta de usuário (Home), pois a sua cópia ficaria desatualizada em poucos minutos.

A Solução: Ponteiros de Atalho

Em situações complexas de gerenciamento de caminhos como esta, os Links entram em ação como recursos extremamente valiosos. No Linux, você pode criar um novo arquivo em uma localização conveniente e de fácil alcance (como diretamente dentro do seu diretório Home) que atua rigidamente conectado ao arquivo original profundamente enterrado.

Sempre que você tentar ler, editar ou inspecionar este novo arquivo de atalho local, o sistema operacional interceptará a chamada e acessará de forma transparente e instantânea os dados e blocos de disco contidos no arquivo real valuable-information.txt.

As Duas Metodologias de Vinculação: O Linux disponibiliza dois métodos distintos para a criação desses vínculos no sistema de arquivos: os **Links Físicos (Hard Links)** e os **Links Simbólicos (Symbolic Links ou Soft Links)**.

Embora ambas as abordagens forneçam o mesmo resultado visual de acesso para o usuário final, elas utilizam técnicas internas e manipulações de nós de índice (Inodes) completamente diferentes por baixo do capô. Existem vantagens e desvantagens severas para cada método, tornando fundamental o entendimento de ambas as mecânicas para saber exatamente quando implementar cada uma no dia a dia da administração de sistemas.

18.5.1 Criando Links Físicos (Hard Links)

Para compreender profundamente o funcionamento dos Links Físicos (Hard Links), é crucial entender primeiro como o sistema de arquivos do Linux rastreia, indexa e organiza os elementos no disco.

Para cada arquivo criado, existe uma estrutura de dados de tamanho fixo no sistema de arquivos dedicada a armazenar exclusivamente os seus metadados. Esses metadados englobam propriedades vitais como permissões de acesso, donos e grupos proprietários, e carimbos de data/hora (timestamps). O nome do arquivo e o seu conteúdo textual bruto não ficam guardados aqui; no entanto, quase todas as outras informações estruturais sobre o arquivo residem nessa área.

Essa estrutura de controle de metadados chama-se Tabela de Inodes (Nós de Índice). Cada inode individual possui ponteiros lógicos que apontam para os blocos físicos reais no disco (chamados de data blocks) onde o conteúdo do arquivo está de fato escrito.

O Número de Inode e a Estrutura de Diretórios

Cada arquivo dentro de uma mesma partição de disco recebe um número identificador exclusivo conhecido como Número de Inode. Da mesma forma que usuários e grupos são identificados pelo kernel através de IDs numéricos e não por seus nomes de texto, o que define um arquivo no sistema operacional é estritamente o seu número de inode associado.

Você pode inspecionar e exibir o número de inode de qualquer elemento adicionando a flag -i ao comando de listagem (ls -i): 

sysadmin@localhost:~$ ls -i /tmp/file.txt
215220874 /tmp/file.txt

Como a tabela de inodes não armazena o nome do arquivo, onde os nomes ficam guardados? A resposta é simples: dentro da área de dados do diretório pai. Uma pasta no Linux nada mais é do que um arquivo especial cujo conteúdo interno é uma tabela simples contendo associações diretas entre nomes de arquivos textuais e seus respectivos números de Inodes.

Veja um exemplo conceitual de como o conteúdo do bloco de dados do diretório /etc é organizado internamente:

Nome do Arquivo Número de Inode
passwd 123
shadow 175
group 144
gshadow 897

Quando você executa o comando more /etc/passwd, o kernel consulta essa tabela interna da pasta /etc para traduzir o nome informado no ID 123. Em seguida, ele localiza o inode 123 na tabela global do sistema de arquivos e segue seus ponteiros para ler os blocos de dados contidos no disco.

O que é, tecnicamente, um Hard Link?

Um Link Físico (Hard Link) nada mais é do que a criação de duas ou mais entradas de nomes diferentes dentro de diretórios que apontam exatamente para o **mesmo número de inode**. Considere o exemplo de mapeamento abaixo:

Nome do Arquivo Número de Inode
passwd 123
mypasswd 123
shadow 175
group 144

Como os nomes passwd e mypasswd compartilham rigorosamente o mesmo número de inode, eles são essencialmente o mesmo arquivo físico. Qualquer alteração ou gravação feita através de um nome será instantaneamente visível pelo outro, pois ambos manipulam os mesmos blocos de dados no disco rígido.

O Contador de Links (Link Count)

Quando executamos uma listagem longa detalhada com as flags -li, o número exibido pelo sistema logo após a string de permissões e antes do nome do usuário dono representa o Contador de Links Físicos daquele elemento: 

sysadmin@localhost:~$ echo data > file.original
sysadmin@localhost:~$ ls -li file.*
278772 -rw-rw-r--. 1 sysadmin sysadmin 5 Oct 25 15:42 file.original

Esse contador indica quantos nomes textuais no sistema de arquivos estão vinculados àquele nó de índice. Um valor igual a 1 significa que aquele inode possui apenas uma única referência de nome apontando para ele.

Criando Hard Links com o comando ln

Para criar links físicos no Linux, utilizamos o comando nativo ln passando dois argumentos básicos: o primeiro é o arquivo real já existente (chamado de target ou alvo) e o segundo é o novo nome de atalho que será gerado (o link_name): 

ln target nome_do_link

Cada vez que o utilitário ln é executado com sucesso para gerar um novo link físico, o contador de referências do inode correspondente é incrementado em uma unidade de forma automática: 

sysadmin@localhost:~$ ln file.original file.hard.1
sysadmin@localhost:~$ ls -li file.*
278772 -rw-rw-r--. 2 sysadmin sysadmin 5 Oct 25 15:53 file.hard.1
278772 -rw-rw-r--. 2 sysadmin sysadmin 5 Oct 25 15:53 file.original

Observe que ambos os arquivos agora exibem o mesmo número de inode (278772) e o contador de links físicos subiu para 2. Não existe mais uma distinção hierárquica entre quem é o arquivo original e quem é o link; ambos possuem o mesmo peso e autoridade sobre os blocos de dados.

18.5.2 Criando Links Simbólicos (Symbolic Links)

Um Link Simbólico (também conhecido como Symbolic Link ou Soft Link) funciona de maneira totalmente diferente de um link físico. Em vez de compartilhar o mesmo nó de índice, ele é **um arquivo independente que armazena, como seu conteúdo interno, um texto contendo o caminho (ponteiro) para outro arquivo**.

Existem diversos links simbólicos nativos configurados para manter a compatibilidade estrutural do ecossistema Linux. Veja um exemplo clássico localizado dentro do diretório /etc: 

sysadmin@localhost:~$ ls -l /etc/grub.conf
lrwxrwxrwx. 1 root root 22 Feb 15  2011 /etc/grub.conf -> ../boot/grub/grub.conf

No exemplo acima, o arquivo /etc/grub.conf "aponta diretamente para" o arquivo ../boot/grub/grub.conf. Portanto, se você tentar ler ou inspecionar o conteúdo de /etc/grub.conf, o kernel interceptará a chamada, seguirá o ponteiro textual de forma transparente e exibirá os dados contidos no arquivo real de destino do Grub.

Criando Soft Links com a flag -s

Para gerar um link simbólico, utilizamos o mesmo comando ln, porém adicionando obrigatoriamente a opção -s (symbolic). A sintaxe padrão segue a ordem de destino e atalho: 

ln -s target nome_do_link

Veja a simulação de criação de um atalho simbólico local para o arquivo de contas do sistema:

sysadmin@localhost:~$ ln -s /etc/passwd mypasswd
sysadmin@localhost:~$ ls -l mypasswd
lrwxrwxrwx. 1 sysadmin sysadmin 11 Oct 31 13:17 mypasswd -> /etc/passwd
Considere Isto: Identificação do Tipo de Arquivo Repare atentamente no output do comando ls -l para o link recém-criado: o primeiríssimo caractere da string de permissões é a letra l. Esse indicador de metadados avisa explicitamente ao administrador que o tipo daquele arquivo é um link simbólico, diferenciando-o de arquivos comuns (-) ou diretórios (d).

Além disso, os bits de permissões de um link simbólico aparecem quase sempre como rwxrwxrwx (777). No entanto, isso é apenas uma convenção conceitual: o acesso real aos dados será controlado unicamente pelas permissões de segurança associadas ao arquivo de destino final (o target).

18.5.3 Comparando Links Físicos e Simbólicos

Embora os links físicos e simbólicos entreguem o mesmo resultado prático para o usuário final (o acesso transparente aos dados de um arquivo), as diferentes técnicas estruturais de cada abordagem produzem vantagens e desvantagens cruciais. Na verdade, os pontos fortes de uma metodologia compensam diretamente as limitações da outra.

Vantagem: Links Físicos não possuem ponto único de falha

Um dos maiores benefícios do link físico é que cada nome associado ao conteúdo do arquivo possui exatamente o mesmo peso hierárquico e autoridade. Se você tiver cinco arquivos conectados por links físicos ao mesmo inode, deletar quatro desses nomes não apagará os dados reais do arquivo no disco.

Como o arquivo está atrelado a um nó de índice exclusivo, enquanto houver ao menos um link físico remanescente apontando para aquele inode, o contador de links será maior que zero, mantendo o nó ativo e os blocos de dados perfeitamente intactos.

O Comportamento Frágil do Link Simbólico:

Os links simbólicos, por outro lado, possuem um ponto único de falha bem definido: o arquivo original de destino. Se o alvo for removido, o atalho se rompe e fica inutilizável (comportamento conhecido como link órfão ou quebrado). Veja a simulação: 

sysadmin@localhost:~$ ls -l mytest.txt
lrwxrwxrwx. 1 sysadmin sysadmin 8 Oct 31 13:29 mytest.txt -> test.txt
sysadmin@localhost:~$ more test.txt
hi there
sysadmin@localhost:~$ more mytest.txt
hi there

Se removermos o arquivo base test.txt, o link aponta para o vazio e falha imediatamente: 

sysadmin@localhost:~$ rm test.txt
sysadmin@localhost:~$ more mytest.txt
mytest.txt: No such file or directory
sysadmin@localhost:~$ ls -l mytest.txt
lrwxrwxrwx. 1 sysadmin sysadmin 8 Oct 31 13:29 mytest.txt -> test.txt

Vantagem: Links Simbólicos são muito mais fáceis de visualizar

Auditar e mapear links físicos pode ser uma tarefa complexa, pois o sistema operacional não indica nativamente para onde os outros nomes apontam. Se você visualizar um arquivo regular com um contador de links maior que um, precisará extrair o número do inode com o comando ls -i e fazer uma varredura na partição usando o utilitário find com o critério -inum para localizar os outros clones: 

sysadmin@localhost:~$ ls -i file.original
278772 file.original
sysadmin@localhost:~$ find / -inum 278772 2> /dev/null
/home/sysadmin/file.hard.1
/home/sysadmin/file.original

Os links simbólicos eliminam essa barreira logística por serem totalmente visuais. Uma simples listagem com o comando ls -l expõe a rota do ponteiro e o destino final do atalho na tela sem a necessidade de comandos adicionais: 

sysadmin@localhost:~$ ls -l mypasswd
lrwxrwxrwx. 1 sysadmin sysadmin 11 Oct 31 13:17 mypasswd -> /etc/passwd

Vantagem: Soft Links podem cruzar diferentes sistemas de arquivos

Como cada partição de disco ou sistema de arquivos possui a sua própria tabela isolada de inodes, é tecnicamente impossível criar links físicos que cruzem diferentes partições. Tentar forçar essa ligação gera um erro clássico do kernel: 

sysadmin@localhost:~$ ln /boot/vmlinuz-2.6.32-358.6.1.el6.i686 Linux.Kernel
ln: creating hard link `Linux.Kernel' => `/boot/vmlinuz-2.6.32-358.6.1.el6.i686': Invalid cross-device link

No exemplo acima, a tentativa de vincular a pasta /boot (uma partição dedicada) com a raiz / falhou porque os IDs de inodes não podem ser exportados fora de seus limites lógicos.

Contudo, como o link simbólico aponta para caminhos textuais (pathnames) e não para os IDs numéricos de inodes, ele consegue contornar essa restrição sem nenhuma dificuldade: 

sysadmin@localhost:~$ ln -s /boot/vmlinuz-2.6.32-358.6.1.el6.i686 Linux.Kernel
sysadmin@localhost:~$ ls -l Linux.Kernel
lrwxrwxrwx. 1 sysadmin sysadmin 11 Oct 31 13:17 Linux.Kernel -> /boot/vmlinuz-2.6.32-358.6.1.el6.i686

Vantagem: Soft Links podem apontar para diretórios

Outra limitação arquitetural estrita dos links físicos é que eles não podem ser criados sobre diretórios. Essa barreira existe para evitar que usuários gerem loops infinitos ou inconsistências na própria hierarquia estrutural que o kernel usa para indexar a árvore do sistema. Tentar realizar essa ação resultará em um bloqueio explícito: 

sysadmin@localhost:~$ ln /bin binary
ln: `/bin': hard link not allowed for directory

Novamente, a flexibilidade dos links simbólicos resolve o problema de maneira perfeitamente legalizada: 

sysadmin@localhost:~$ ln -s /bin binary
sysadmin@localhost:~$ ls -l binary
lrwxrwxrwx. 1 sysadmin sysadmin 11 Oct 31 13:17 binary -> /bin
