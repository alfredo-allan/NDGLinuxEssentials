Módulo 16

Criação de Usuários e Grupos

Aprendendo a planejar, provisionar e modificar contas de usuários e grupos através da linha de comando no Linux.

16.1 Introdução

Durante o processo de instalação do sistema, a maioria dos instaladores cria um usuário comum inicial e concede a ele a permissão para executar comandos administrativos via sudo, ou exige que uma senha para a conta do usuário root seja configurada. Quase todos os sistemas Linux são estruturados para permitir que ao menos um usuário sem privilégios faça login e tenha a capacidade de executar comandos como root, direta ou indiretamente.

Se o computador for utilizado por apenas uma pessoa, ter uma única conta de usuário comum pode ser o suficiente. No entanto, se uma máquina precisa ser compartilhada por múltiplos indivíduos, torna-se desejável ter uma conta separada e exclusiva para cada pessoa.

Vantagens de Contas Individuais

Acesso Seletivo: As contas são usadas para conceder acessos específicos a arquivos ou serviços. Por exemplo, cada conta possui seu próprio diretório home (diretório pessoal), que por padrão não pode ser acessado por outros usuários comuns.

Rastreabilidade com Sudo: O comando sudo pode ser configurado para liberar apenas comandos administrativos selecionados. Ao exigir o uso do sudo para tarefas críticas, o sistema gera logs detalhados de qual usuário executou cada ação.

Flexibilidade de Gerenciamento: Cada conta individual pode ter suas próprias associações a grupos e direitos específicos, permitindo um controle muito mais maleável da infraestrutura.

Grupos Privados de Usuário (UPG)

Em algumas distribuições, a criação de uma nova conta de usuário gera automaticamente uma conta de grupo correspondente chamada de User Private Group (UPG) ou Grupo Privado do Usuário. Nesses sistemas, o nome do grupo e o nome do usuário serão idênticos, e o único membro inicial desse grupo recém-criado será o próprio usuário correspondente.

Para as distribuições que não adotam o padrão de UPG, as novas contas geralmente recebem um grupo genérico chamado users como seu grupo primário. Independentemente do método, os usuários podem ser modificados a qualquer momento para entrar ou sair de grupos, mas devem obrigatoriamente pertencer a pelo menos um grupo para atuar como seu grupo primário.

Dica de Planejamento Administrativo: Antes de começar a criar usuários de forma desordenada, você deve planejar como utilizará as estruturas de grupos. É muito mais eficiente criar primeiro os seus grupos de colaboração e, em seguida, provisionar os usuários já vinculando-os às suas respectivas associações. Caso faça o oposto (criar os usuários primeiro e os grupos depois), você terá o retrabalho de executar etapas extras de modificação para cada um dos usuários.

16.2 Grupos (Groups)

O motivo mais comum para se criar um grupo no Linux é fornecer um meio prático para que os usuários compartilhem arquivos e colaborem entre si.

Considere um cenário onde várias pessoas trabalham juntas no mesmo projeto e precisam editar ou visualizar documentos em comum armazenados no servidor. Para resolver isso, o administrador do sistema pode tornar essas pessoas membras de um grupo em comum, alterar a propriedade (ownership) do diretório do projeto para este novo grupo e ajustar as permissões do diretório para permitir que todos os membros do grupo acessem e manipulem os arquivos ali dentro.

Após criar ou modificar um grupo, você pode verificar se as alterações foram aplicadas corretamente consultando as informações de configuração do grupo diretamente no arquivo /etc/group utilizando o comando grep.

Caso você esteja trabalhando em um ambiente corporativo com serviços de autenticação baseados em rede (como LDAP ou Active Directory), o comando getent é o mais indicado, pois exibe tanto os grupos locais quanto os mapeados via rede. 

grep padrão arquivo
getent banco_de_dados registro

Para uso estritamente local, ambos os comandos retornarão exatamente o mesmo resultado. Veja o exemplo de consulta realizado para o grupo do superusuário root: 

root@localhost:~# grep root /etc/group
root:x:0:
root@localhost:~# getent group root
root:x:0:

16.2.1 Criando um Grupo

O comando groupadd pode ser executado pelo usuário root para criar um novo grupo no sistema. Em sua sintaxe mais simples, o comando exige apenas o nome do grupo que se deseja criar.

Caso seja necessário determinar um ID específico, a opção -g pode ser utilizada para especificar manualmente o GID (Group ID) do novo grupo: 

root@localhost:~# groupadd -g 1005 research
root@localhost:~# grep research /etc/group
research:x:1005:

Se a opção -g não for fornecida durante a execução, o comando groupadd atribuirá automaticamente um GID para o novo grupo.

Para realizar essa atribuição automatizada, o binário analisa o arquivo /etc/group e seleciona um número que seja exatamente uma unidade maior (+1) do que o maior GID atualmente em uso no sistema. A execução dos comandos abaixo ilustra esse comportamento sequencial: 

root@localhost:~# groupadd development
root@localhost:~# grep development /etc/group
development:x:1006:

16.2.1.1 Considerações sobre GID

Em algumas distribuições Linux, particularmente aquelas baseadas em Red Hat, quando um ID de usuário (UID) é criado, um grupo privado de usuário (UPG) também é criado com esse usuário como seu único membro. Nessas distribuições, o UID e o ID do UPG correspondente devem ser idênticos (possuir o mesmo número).

Portanto, ao gerenciar o sistema, você deve evitar criar GIDs nos mesmos intervalos numéricos onde planeja criar UIDs. Isso previne o risco de conflito entre um GID criado manualmente por você e um número de UPG gerado de forma automática para corresponder a um novo UID.

Intervalos de IDs Reservados: GIDs abaixo de 500 (no padrão Red Hat) ou de 1.000 (no padrão Debian/Ubuntu) são estritamente reservados para o uso de contas e serviços do próprio sistema operacional.

Eventualmente, você pode precisar criar e atribuir um GID de sistema de valor mais baixo para um novo serviço. Para alcançar esse resultado, utilize a opção -r, que instrui o comando a alocar para o novo grupo um GID que seja menor do que o menor GID padrão de usuários comuns: 

root@localhost:~# groupadd -r sales
root@localhost:~# getent group sales
sales:x:999:

16.2.1.2 Considerações sobre Nomes de Grupos

Seguir diretrizes padronizadas para a nomenclatura de grupos ajuda a garantir que o nome escolhido seja portável (ou seja, que funcione corretamente de forma integrada com outros sistemas operacionais, scripts ou serviços de diretório).

As boas práticas recomendadas para a definição de nomes de grupos incluem:

Regras de Sintaxe

Regra Descrição Técnica
Primeiro Caractere Deve ser obrigatoriamente um caractere de sublinhado (_) ou uma letra minúscula de a-z.
Comprimento Máximo A maioria das distribuições Linux aceita nomes de até 32 caracteres. No entanto, utilizar mais do que 16 caracteres pode causar problemas de compatibilidade em ambientes legados.
Caracteres Restantes Após o primeiro caractere, são permitidos caracteres alfanuméricos, hífens (-) ou sublinhados (_).
Último Caractere O nome do grupo não deve terminar com um hífen (-).
Nota de Compatibilidade: Infelizmente, essas diretrizes nem sempre são validadas de forma rígida pelo sistema operacional. O risco real não está no comando groupadd falhar ao criar um nome fora dos padrões, mas sim no fato de que outros comandos, scripts automatizados ou daemons de rede podem não funcionar corretamente ao processar caracteres inesperados.

16.2.2 Modificando um Grupo

O comando groupmod é utilizado na administração do sistema para alterar as propriedades de um grupo existente. Suas principais flags são a opção -n (para alterar o nome de um grupo) e a opção -g (Rh-b para alterar o GID numérico do grupo).

Alterar o nome de um grupo pode confundir os usuários que estavam habituados com a nomenclatura antiga. No entanto, do ponto de vista técnico, renomear um grupo não causará nenhum problema de acesso a arquivos, pois o kernel do Linux gerencia a propriedade dos arquivos através dos GIDs numéricos, e não por strings de texto. Veja o exemplo: 

root@localhost:~# ls -l index.html
-rw-r-----. 1 root sales 0 Aug  1 13:21 index.html
root@localhost:~# groupmod -n clerks sales
root@localhost:~# ls -l index.html
-rw-r-----. 1 root clerks 0 Aug  1 13:21 index.html
Nota do Laboratório: O arquivo index.html utilizado no exemplo acima serve apenas para ilustração didática e não está fisicamente disponível dentro da máquina virtual deste curso.

Como observado após a execução do comando groupmod -n, o arquivo passou a exibir um nome de grupo proprietário diferente (clerks). No entanto, todos os usuários que pertenciam ao antigo grupo sales continuam associados ao mesmo ID interno e agora fazem parte do grupo clerks, mantendo seu acesso intacto ao arquivo.

Risco Crítico ao Alterar o GID: Por outro lado, se você optar por alterar o GID numérico de um grupo existente, todos os arquivos previamente associados àquele grupo perderão o vínculo textual com o nome dele. Na realidade, o sistema deixará de mapear qualquer nome de grupo para esses arquivos, exibindo apenas o GID numérico antigo órfão no output do comando ls: 
root@localhost:~# groupmod -g 10003 clerks
root@localhost:~# ls -l index.html
-rw-r-----. 1 root 491 13370 Aug  1 13:21 index.html
Considere Isto: Arquivos Órfãos (Orphaned Files) Arquivos no sistema de arquivos que apontam para um GID sem nome associado no /etc/group são conhecidos como arquivos órfãos. Para varrer o sistema em busca de todos os arquivos associados a um ID de grupo inexistente, utilize a opção -nogroup combinada ao comando find: 
root@localhost:~# find / -nogroup 
/root/index.html

16.2.3 Excluindo um Grupo

Se você decidir excluir um grupo utilizando o comando groupdel, fique atento ao fato de que quaisquer arquivos que pertenciam a esse grupo perderão sua referência textual e se tornarão arquivos órfãos (mantendo apenas o antigo GID numérico gravado nos metadados).

Restrição Importante: Apenas grupos suplementares (secundários) podem ser excluídos diretamente do sistema. Se um grupo estiver definido atualmente como o grupo primário de qualquer usuário, o comando groupdel recusará a ação e falhará.

Para contornar essa restrição, o administrador deve primeiro modificar a conta do usuário em questão, definindo um grupo diferente como seu grupo primário. Uma vez que o grupo antigo passe a ser apenas um grupo secundário ou fique totalmente sem usuários associados, ele poderá ser removido de forma definitiva.

Certificando-se de que o grupo alvo não é o grupo primário de ninguém, a exclusão é efetuada passando o comando groupdel acompanhado do nome do grupo: 

root@localhost:~# groupdel clerks

16.3 Usuários (Users)

Como estudado anteriormente, as informações cadastrais das contas de usuário ficam armazenadas no arquivo /etc/passwd, enquanto as informações de autenticação (os dados das senhas criptografadas) ficam guardadas no arquivo /etc/shadow.

A criação de um novo usuário poderia ser feita inserindo manualmente uma nova linha de texto no final de cada um desses arquivos, mas essa técnica geralmente não é recomendada em ambientes de produção.

Risco de Corrupção de Arquivos: Ao utilizar os comandos apropriados para provisionar um novo usuário, esses arquivos críticos do sistema são modificados de forma automatizada, encadeada e segura. Se você tentasse alterá-los manualmente usando um editor de texto comum, correria o risco de cometer um erro de sintaxe ou de digitação que poderia corromper a base de dados e impedir que todos os usuários do sistema fizessem login normalmente.

Antes de começar a criar contas de usuários no seu sistema operacional, é uma excelente prática administrativa verificar ou estabelecer valores práticos que serão aplicados por padrão sempre que o comando useradd for invocado.

Essas diretrizes de comportamento padrão ficam guardadas em arquivos específicos de configuração que servem de base para o utilitário useradd.

Boa Prática de Automação: Garantir que os valores dentro desses arquivos de configuração padrão sejam razoáveis e estejam de acordo com a política de segurança da sua empresa antes de adicionar os usuários poupará muito tempo e trabalho, evitando que você tenha que corrigir manualmente as definições de cada conta após o provisionamento em lote.

16.3.1 Arquivos de Configuração de Usuário

A opção -D do comando useradd permite que você visualize ou altere alguns dos valores padrões utilizados no provisionamento de novas contas. Os parâmetros exibidos pelo comando useradd -D também podem ser visualizados ou atualizados manipulando diretamente o arquivo de configuração /etc/default/useradd: 

root@localhost:~# useradd -D 
GROUP=100
HOME=/home
INACTIVE=-1
EXPIRE=
SHELL=/bin/bash
SKEL=/etc/skel
CREATE_MAIL_SPOOL=yes

Abaixo descrevemos detalhadamente o impacto técnico de cada um desses valores padrão:

Grupo Padrão (GROUP) 

GROUP=100

Em distribuições que não utilizam o conceito de UPG (User Private Group), este define o grupo primário padrão para um novo usuário caso nenhum outro seja especificado com o comando. Normalmente, aponta para o grupo users com GID 100.

Essa configuração afeta diretamente o campo de ID do grupo primário no arquivo /etc/passwd destacado abaixo:

bob:x:600:600:bob:/home/bob:/bin/bash

Nota: A opção -g do comando useradd permite que você defina um grupo primário diferente do padrão no momento da criação.

Diretório Base Home (HOME) 

HOME=/home

O diretório /home atua como a pasta base padrão sob a qual o diretório pessoal de cada novo usuário será criado. Isso significa que um usuário com a conta chamada bob receberá a home em /home/bob.

Essa configuração afeta o campo de diretório home do arquivo /etc/passwd destacado abaixo:

bob:x:600:600:bob:/home/bob:/bin/bash

Nota: A opção -b do comando useradd permite definir um diretório base diferente para a home durante o provisionamento.

Período de Inatividade (INACTIVE) 

INACTIVE=-1

Este valor representa a quantidade de dias tolerados após o vencimento de uma senha para que a conta seja desativada por completo pelo sistema. O valor -1 desabilita esse recurso, significando que nenhuma data de inatividade será aplicada por padrão para novas contas.

Essa configuração afeta o campo de inatividade do arquivo /etc/shadow destacado abaixo:

bob:pw:15020:5:30:7:60:15050:

Nota: A opção -f do comando useradd permite que você configure um valor de inatividade customizado.

Data de Expiração (EXPIRE) 

EXPIRE=

Por padrão, não há nenhuma data de encerramento global definida. Normalmente, prazos de validade são estipulados para contas individuais e temporárias, e não para todos os usuários criados no sistema.

Por exemplo, se um prestador de serviço foi contratado para trabalhar apenas até o final do dia 1 de novembro de 2019, você pode garantir o bloqueio do login configurando este campo na conta dele.

Essa configuração afeta o campo de expiração da conta do arquivo /etc/shadow destacado abaixo:

bob:pw:15020:5:30:7:60:15050:

Nota: A opção -e do comando useradd permite definir uma data de expiração específica para uma conta.

Shell Padrão (SHELL) 

SHELL=/bin/bash

Indica qual interpretador de comandos será atribuído ao usuário por padrão assim que ele se autenticar no ambiente de terminal.

Essa configuração afeta o campo do shell de login no arquivo /etc/passwd destacado abaixo:

bob:x:600:600:bob:/home/bob:/bin/bash

Nota: A opção -s do comando useradd permite que você especifique um shell diferente no momento do provisionamento.

Diretório Esqueleto (SKEL) 

SKEL=/etc/skel

O valor de SKEL determina qual diretório modelo (esqueleto) terá todo o seu conteúdo e arquivos ocultos clonados para dentro do novo diretório home do usuário. O sistema realiza a cópia e altera automaticamente o proprietário (ownership) desses novos arquivos para o usuário recém-criado.

Esse recurso fornece aos administradores uma forma simples de popular novos perfis com variáveis e perfis de inicialização padronizados (como .bashrc e .profile).

Nota: A opção -k do comando useradd permite utilizar um diretório esqueleto alternativo.

Criar Caixa de E-mail (CREATE_MAIL_SPOOL) 

CREATE_MAIL_SPOOL=yes

Um mail spool é um arquivo de sistema onde as mensagens recebidas locais são armazenadas. O valor definido como yes configura por padrão a habilidade de receber e armazenar mensagens internas no servidor. Se você não pretende operar serviços de e-mail local, este valor pode ser alterado para no.

Como Modificar as Configurações Padrão: Embora você possa editar o arquivo /etc/default/useradd diretamente com um editor de texto, uma abordagem muito mais segura para realizar atualizações controladas é invocar o próprio comando useradd -D acompanhado do parâmetro desejado.

Por exemplo, se você deseja que as senhas expiradas de novos usuários ainda permitam logins e carências por até 30 dias antes do bloqueio da conta, execute o seguinte comando: 

root@localhost:~# useradd -D -f 30
root@localhost:~# useradd -D
GROUP=100
HOME=/home
INACTIVE=30
EXPIRE=
SHELL=/bin/bash
SKEL=/etc/skel
CREATE_MAIL_SPOOL=yes

16.3.2 Diretrizes Globais com o login.defs

O arquivo /etc/login.defs também armazena valores que são aplicados por padrão aos novos usuários criados através do comando useradd. Diferente do arquivo /etc/default/useradd, o arquivo /etc/login.defs é rotineiramente editado de forma direta pelo administrador com um editor de texto sempre que há necessidade de alterar suas diretrizes.

Como este arquivo é composto por muitos comentários explicativos e linhas em branco, você pode filtrar a saída do terminal para exibir apenas as configurações de fato ativas utilizando a seguinte expressão regular com o comando grep: 

root@localhost:~# grep -Ev '^#|^$' /etc/login.defs
MAIL_DIR	/var/mail/spool
PASS_MAX_DAYS	99999
PASS_MIN_DAYS	0
PASS_MIN_LEN	5
PASS_WARN_AGE	7
UID_MIN			  500
UID_MAX			60000
GID_MIN			  500
GID_MAX			60000
CREATE_HOME	yes
UMASK           077
USERGROUPS_ENAB yes
ENCRYPT_METHOD SHA512
MD5_CRYPT_ENAB no

O exemplo acima reflete a estrutura típica de um arquivo /etc/login.defs de uma distribuição CentOS 6. Abaixo, detalhamos o significado e a função de cada um desses parâmetros:

Diretório de Correio (MAIL_DIR) 

MAIL_DIR	/var/mail/spool

Especifica o caminho absoluto do diretório do sistema onde o arquivo de spool de e-mail local do usuário será criado.

Validade Máxima da Senha (PASS_MAX_DAYS) 

PASS_MAX_DAYS	99999

Determina a quantidade máxima de dias que um usuário pode continuar utilizando a mesma senha. Sendo o padrão 99999 dias (o que ultrapassa 270 anos), isso significa que a troca nunca será exigida de forma compulsória pelo sistema.

Organizações que seguem políticas rígidas de segurança corporativa costumam reduzir este parâmetro para 30 ou 60 dias. Esta variável preenche por padrão o campo destacado no arquivo /etc/shadow: 

bob:pw:15020:5:30:7:60:15050:

Intervalo Mínimo de Troca (PASS_MIN_DAYS) 

PASS_MIN_DAYS	0

Sendo zero (0) o padrão, o tempo mínimo exigido para o usuário manter uma senha é nulo. Isso significa que ele pode redefinir sua senha e, imediatamente em sequência, alterá-la de volta para o valor que quiser.

Se este valor fosse configurado, por exemplo, para 3 dias, o usuário seria obrigado a esperar esse intervalo antes de conseguir efetuar uma nova troca. Esta variável reflete o campo destacado no arquivo /etc/shadow: 

bob:pw:15020:3:30:7:60:15050:

Comprimento Mínimo da Senha (PASS_MIN_LEN) 

PASS_MIN_LEN	5

Estipula a quantidade mínima de caracteres que o sistema aceitará ao validar a criação de uma nova senha.

Aviso de Expiração (PASS_WARN_AGE) 

PASS_WARN_AGE	7

Determina o comportamento padrão para o campo de alertas de expiração. Conforme o usuário se aproxima da quantidade máxima de dias permitidos para o uso daquela senha, o Linux começará a disparar avisos preventivos durante o procedimento de login.

Esta configuração alimenta o campo destacado no arquivo /etc/shadow:

bob:pw:15020:3:30:7:60:15050:

Limites de UID (UID_MIN / UID_MAX) 

UID_MIN		500
UID_MAX		60000

O parâmetro UID_MIN estabelece o primeiro identificador numérico que será atribuído a uma conta de usuário comum comum. Qualquer valor abaixo deste limite fica reservado exclusivamente para o uso do root e de contas de serviços do sistema. O UID_MAX limita o teto seguro de IDs para manter a compatibilidade em ambientes legados.

Limites de GID (GID_MIN / GID_MAX) 

GID_MIN		500
GID_MAX		60000

Assim como os UIDs, o GID_MIN define o número inicial para novos grupos de usuários comuns. Para garantir o pleno funcionamento da estrutura de Grupos Privados de Usuário (UPG), os tetos máximos de UID_MAX e GID_MAX devem ser mantidos com o mesmo valor.

Geração Automática de Home (CREATE_HOME) 

CREATE_HOME	yes

O valor definido aqui determina se um novo diretório pessoal será ou não gerado fisicamente no disco no mesmo instante em que a conta do usuário for inserida.

Máscara de Permissões (UMASK) 

UMASK           077

A variável UMASK atua diretamente no instante em que o diretório home do usuário é criado, definindo quais permissões restritivas padrão serão aplicadas a essa pasta. Utilizar a máscara padrão 077 significa remover todo e qualquer privilégio de outros grupos e terceiros, fazendo com que apenas o proprietário da conta consiga acessar e listar os arquivos daquela home.

Habilitar Grupos Privados (USERGROUPS_ENAB) 

USERGROUPS_ENAB yes

Em distribuições que implementam a arquitetura de criar um grupo exclusivo para cada usuário (como o CentOS e o Ubuntu), esta variável assume o valor yes. Caso a distribuição adote um grupo genérico compartilhado para novos usuários comuns, o valor será configurado como no.

Algoritmo de Criptografia (ENCRYPT_METHOD / MD5_CRYPT_ENAB) 

ENCRYPT_METHOD SHA512
MD5_CRYPT_ENAB no

Determina qual algoritmo criptográfico de hash de via única será utilizado para embaralhar e proteger as senhas no arquivo /etc/shadow. Atualmente, o padrão de segurança recomendado é o SHA512. A linha MD5_CRYPT_ENAB no refere-se a um método legado (MD5) que foi inteiramente descontinuado e substituído pelo parâmetro moderno de criptografia do sistema.

16.3.3 Considerações sobre Contas

O provisionamento de uma conta de usuário em sistemas Linux pode exigir o levantamento prévio de diversas informações de infraestrutura. Embora o único argumento estritamente obrigatório seja o nome da conta, um bom planejamento administrativo deve considerar o mapeamento do UID, do grupo primário, dos grupos suplementares, do diretório home, do diretório esqueleto (skel) e do shell de login que serão utilizados.

Nome de Usuário (Username)

O nome da conta é o único argumento obrigatório do comando useradd. Ele deve seguir rigorosamente as mesmas diretrizes de portabilidade especificadas para os nomes de grupos (letras minúsculas de a-z ou sublinhado _ no primeiro caractere, máximo de 16 a 32 caracteres, sem hífens no final).

Se o usuário precisa acessar múltiplos servidores na rede, é altamente recomendável que o nome da conta seja idêntico em todas as máquinas. O nome de usuário deve ser exclusivo no sistema. 

root@localhost:~# useradd jane

Identificador de Usuário (UID)

Por padrão, após a criação de um usuário, o sistema incrementa o UID em uma unidade (+1) para a próxima conta. Em redes corporativas, garanta que o UID de um mesmo funcionário seja idêntico em todos os servidores para manter a consistência nas permissões de rede.

A flag -u permite estipular um número de UID customizado. Para máxima compatibilidade com sistemas legados, o teto recomendado é de 60.000. 

root@localhost:~# useradd -u 1000 jane
Risco de Segurança com UID 0: O usuário root possui o UID 0, o que concede privilégios totais ao sistema. Qualquer outra conta configurada com o UID igual a 0 atuará e terá os mesmos poderes do administrador root, independentemente do nome de texto que possua.

As contas de sistema rodam serviços em background (daemons) sob UIDs reservados (geralmente de 1 a 499 ou de 1 a 999), limitando o raio de destruição caso o serviço seja comprometido. Uma exceção histórica a essa faixa é a conta nfsnobody, que utiliza o UID 65534. Como boa prática em novos sistemas, inicie os UIDs de usuários comuns a partir de 1000.

Grupo Primário e Suplementar

Em distribuições com UPG, o grupo primário homônimo é criado junto com o usuário. Caso contrário, o sistema adota o grupo padrão users (GID 100).

Use a flag -g para especificar um grupo primário customizado (por nome ou GID) e a flag -G para associar o usuário a uma lista de grupos suplementares (secundários) separados por vírgula: 

root@localhost:~# useradd -g users jane
root@localhost:~# useradd -G sales,research jane

Diretório Home

A home padrão assume o nome do usuário dentro da pasta base configurada (ex: /home/jane). Veja as opções do comando useradd que gerenciam esse comportamento:

Flag Comportamento Técnico
-M Instrui explicitamente o comando a não criar o diretório home, mesmo se a variável CREATE_HOME estiver ativa.
-m Força a criação física do diretório home (útil se o padrão do sistema estiver desativado).
-b [diretório_base] Determina uma pasta base alternativa para abrigar a home do usuário (ex: -b /test gerará /test/jane).
-d [caminho_completo] Define um caminho absoluto customizado e específico para atuar como o diretório home do usuário.

Veja os exemplos práticos de customização de caminhos da home no terminal:

root@localhost:~# useradd -m jane
root@localhost:~# ls -ld /home/jane                                             
drwxr-xr-x 2 jane jane 4096 Dec 18 19:14 /home/jane

root@localhost:~# useradd -mb /test jane
root@localhost:~# ls -ld /test/jane
drwxr-xr-x 2 jane jane 4096 Dec 18 19:16 /test/jane

root@localhost:~# useradd -md /test/jane jane
root@localhost:~--# ls -ld /test/jane
drwxr-xr-x 2 jane jane 4096 Dec 18 19:19 /test/jane

Diretório Esqueleto (Skeleton Directory)

Por padrão, o conteúdo de /etc/skel é clonado para a home do novo usuário. A flag -k permite apontar para uma pasta modelo alternativa para popular esse novo perfil.

Regra de Sintaxe Obrigatória: Sempre que utilizar a flag -k, você é obrigado a passar também a flag -m. Caso contrário, o comando useradd falhará emitindo um erro. 
root@localhost:~# useradd -mk /home/sysadmin jane
root@localhost:~# ls /home/jane
Desktop  Documents  Downloads  Music  Pictures  Public  Templates  Videos

Shell de Login

O shell padrão pode ser substituído no ato da criação com a flag -s. Para contas de serviços ou de sistema (que não devem realizar interações humanas), adote o shell de bloqueio /sbin/nologin: 

root@localhost:~# useradd -s /bin/bash jane

Campo de Comentário (GECOS)

Originalmente chamado de campo GECOS (General Electric Comprehensive Operating System), o campo de comentário armazena metadados da conta, como o nome completo real do usuário. Vários gerenciadores de login gráfico exibem este valor na tela de autenticação. Defina-o usando a flag -c: 

root@localhost:~# useradd -c 'Jane Doe' jane

16.3.4 Criando um Usuário na Prática

Depois de verificar quais valores padrão serão adotados e reunir todas as informações estruturais necessárias sobre a nova conta, você estará pronto para efetuar o provisionamento do usuário.

O exemplo a seguir demonstra a invocação do comando useradd combinando múltiplas flags de customização em uma única linha: 

root@localhost:~# useradd -u 1009 -g users -G sales,research -m -c 'Jane Doe' jane

Este comando instrui o sistema operacional a criar uma conta com as seguintes especificações técnicas:

  • Nome da Conta (Username): jane
  • ID do Usuário (UID): 1009
  • Grupo Primário (Primary Group): users
  • Grupos Suplementares (Supplementary Groups): sales e research
  • Campo de Comentário (GECOS): Jane Doe
  • Diretório Home: Criação forçada pela flag -m

Imediatamente após a execução do comando, as tabelas de dados do sistema são atualizadas de forma síncrona. Os dados cadastrais básicos e de segurança da usuária são injetados nos arquivos /etc/passwd e /etc/shadow, enquanto os mapeamentos de acessos suplementares são consolidados nos arquivos de grupos /etc/group e /etc/gshadow: 

root@localhost:~# grep jane /etc/passwd
jane:x:1009:100:Jane Doe:/home/jane:/bin/sh

root@localhost:~# grep jane /etc/shadow
jane:!:17883:0:99999:7:30::

root@localhost:~# grep jane /etc/group
research:x:1005:jane
sales:x:999:jane

root@localhost:~# grep jane /etc/gshadow
research:!::jane
sales:!::jane
Aviso Importante de Segurança: Note no arquivo /etc/shadow o caractere de ponto de exclamação (!) no campo do hash. Isso indica que a conta recém-criada **ainda não possui uma senha válida configurada** e permanece temporariamente bloqueada para autenticações externas até que uma senha seja definida.

Adicionalmente, se a diretriz CREATE_MAIL_SPOOL estiver definida como yes nas configurações base, o arquivo de spool de e-mails /var/spool/mail/jane será provisionado automaticamente no sistema: 

root@localhost:~# ls /var/spool/mail
jane  root  rpc  sysadmin

Por fim, devido à inclusão da flag -m, o diretório home /home/jane é gerado fisicamente no disco com permissões restritivas e exclusivas de leitura e escrita para o usuário proprietário. O conteúdo do modelo esqueleto localizado em /etc/skel é integralmente clonado para dentro desta pasta: 

root@localhost:~# ls /home
jane  sysadmin

16.3.5 Políticas de Senhas

Escolher uma boa senha não é uma tarefa simples, mas é crítico que isso seja feito de forma adequada para evitar que a segurança de uma conta (ou de todo o sistema operacional) seja severamente comprometida.

Definir uma senha forte é apenas o primeiro passo; você deve ser extremamente cauteloso para que ela nunca seja revelada a terceiros. Nunca informe sua senha a ninguém e jamais permita que observem você digitando-a. Se optar por anotá-la, guarde-a em um local físico estritamente seguro, como um cofre.

O Perigo de Senhas Previsíveis: É muito fácil criar uma senha fraca por descuido. Se você utilizar qualquer informação pessoal ou contextual que esteja relacionada a você, esses dados poderão ser facilmente descobertos ou minerados por engenharia social. Uma senha segura nunca deve conter dados pessoais seus ou de conhecidos, tais como primeiro nome, sobrenome, data de nascimento, telefone, nomes de animais de estimação ou números de documentos (como CPF e RG).

Fatores para a Escolha de Senhas

Existem inúmeros critérios técnicos que o administrador do sistema deve ponderar ao estabelecer as diretrizes de autenticação do ambiente:

  • Comprimento (Length): O arquivo /etc/login.defs permite que o administrador determine o tamanho mínimo de uma senha. Embora exista o mito de que quanto mais longa a senha, melhor, isso nem sempre é verdade na prática. Senhas excessivamente longas e complexas são difíceis de memorizar e, consequentemente, induzem o usuário a anotá-las em papéis ou arquivos de texto desprotegidos, elevando o risco de exposição.
  • Composição (Composition): Uma senha robusta deve ser composta obrigatoriamente por uma combinação aleatória de caracteres alfabéticos (letras maiúsculas e minúsculas), caracteres numéricos e símbolos/caracteres especiais.
  • Tempo de Vida (Lifetime): Limitar o tempo de validade máxima de uma senha é uma prática recomendada por vários motivos de segurança:
    • Se uma conta for comprometida sem o conhecimento do administrador, o invasor perderá o acesso assim que o prazo expirar e a senha se tornar inválida.
    • Contas antigas ou que não estão sendo utilizadas serão desativadas automaticamente pelo sistema assim que a senha vencer.
    • Se atacantes tentarem uma invasão por força bruta (brute-force attack), a senha será alterada antes que o ataque tenha tempo computacional para ter sucesso.
Efeitos Colaterais de Trocas Excessivas: Exigir que os usuários alterem suas senhas com uma frequência exagerada pode gerar novos problemas de segurança contraintuitivos, tais como:
  • A qualidade e a complexidade das senhas escolhidas pelos usuários tendem a despencar (ex: o usuário passa a apenas incrementar um número no final da palavra).
  • O usuário fatalmente começará a anotar as senhas em post-its ou cadernos, facilitando o roubo físico da credencial.
  • Contas legítimas de uso esporádico expiram frequentemente, sobrecarregando a equipe de suporte e administração com requisições de reset.

Recomendações de Intervalos

As opiniões variam sobre a frequência ideal com que os usuários devem ser forçados a renovar suas credenciais. Para contas de alta sensibilidade ou com privilégios administrativos (como o root e acessos com sudo), recomenda-se uma rotação frequente, como a cada 30 dias.

Por outro lado, para contas comuns de baixa criticidade e sem acesso a dados confidenciais, a necessidade de trocas constantes é menor. Em cenários de risco mínimo, definir uma validade padrão de 90 dias é considerado o balanço mais razoável entre segurança operacional e usabilidade.

16.3.5.1 Configurando uma Senha de Usuário

Existem diferentes maneiras de se alterar a senha de uma conta no Linux. O próprio usuário comum pode rodar o comando passwd, o administrador do sistema pode executar o comando passwd passando o nome do usuário alvo como argumento, ou podem ser utilizadas ferramentas de interface gráfica integradas à distribuição.

O administrador utiliza o comando passwd [nome_do_usuário] tanto para definir a credencial inicial de uma conta recém-criada quanto para resetar senhas esquecidas. No exemplo abaixo, ao disparar o comando para a conta jane, o sistema abre um prompt interativo. Se o procedimento for concluído com sucesso, o hash da nova senha será injetado e salvo diretamente no arquivo /etc/shadow.

Privilégio Absoluto do Root: Enquanto os usuários comuns são obrigados a obedecer a rígidos critérios de complexidade de senhas, o superusuário root precisa seguir apenas uma regra: a senha não pode ser deixada em branco. Se o root decidir violar as diretrizes de segurança impostas pelo sistema, o terminal exibirá avisos de alerta (warnings), mas a regra não será aplicada de forma impeditiva, permitindo que a ação seja concluída. 
root@localhost:~# passwd jane
Enter new UNIX password:
BAD PASSWORD: it is WAY too short
BAD PASSWORD: is too simple
Retype new UNIX password:
passwd: password updated successfully

Após o administrador estipular a credencial inicial, o usuário comum já estará habilitado a realizar o login na máquina utilizando seu nome de conta e senha correspondentes.

Assim que abrir o terminal, o usuário pode invocar o comando passwd **sem nenhum argumento** para alterar e customizar sua própria senha secreta. O sistema solicitará primeiro a senha atual da sessão por motivos de segurança e, na sequência, exigirá a digitação da nova credencial por duas vezes para evitar erros de digitação.

Comportamento para Usuários Comuns: Para um usuário comum, pode ser difícil configurar uma nova senha válida de primeira devido às restrições automáticas de dicionário, comprimento e histórico do Linux. O sistema concede por padrão três tentativas para que o usuário informe uma combinação que satisfaça os pré-requisitos antes que o comando passwd seja abortado com uma mensagem de erro.

Utilizando os privilégios totais do usuário root, os hashes criptografados e todas as demais variáveis de controle e envelhecimento de senhas podem ser auditados abrindo o arquivo /etc/shadow. Vale ressaltar que usuários comuns não possuem os privilégios de leitura (permissão de read) sobre este arquivo confidencial.

16.3.5.2 Gerenciando a Expiração de Senhas (chage)

O comando chage (change age) fornece uma série de opções avançadas para gerenciar as políticas e informações de envelhecimento e expiração de senhas registradas no arquivo /etc/shadow.

Parâmetros do Comando chage

Opção Curta Opção Longa Descrição Técnica
-l --list Lista detalhadamente todas as informações atuais de envelhecimento e expiração da conta.
-d DATA --lastday DATA Define a data da última alteração de senha para a data especificada (formato Epoch ou AAAA-MM-DD).
-E DATA --expiredate DATA Define a data absoluta em que a conta de usuário será desativada e expirada por completo.
-h --help Exibe o menu de ajuda rápida com a sintaxe do comando chage.
-I DIAS --inactive DIAS Estipula o período de carência (dias de inatividade) permitido para login após a senha expirar.
-m DIAS --mindays DIAS Define a quantidade mínima de dias que o usuário deve aguardar antes de poder alterar a senha novamente.
-M DIAS --maxdays DIAS Configura a quantidade máxima de dias que a senha permanece válida antes de exigir a troca.
-W DIAS --warndays DIAS Define quantos dias antes da expiração o sistema começará a emitir avisos de alerta no login.

Um excelente exemplo prático do uso do comando chage é ajustar o tempo de vida máximo da senha de um usuário específico para 60 dias.

No terminal abaixo, alteramos a política da conta jane e, em seguida, validamos a modificação extraindo o quinto campo (campo correspondente ao maxdays) do arquivo /etc/shadow com o comando cut: 

root@localhost:~# chage -M 60 jane
root@localhost:~# grep jane /etc/shadow | cut -d: -f1,5
jane:60

16.3.6 Modificando um Usuário (usermod)

Antes de realizar alterações em uma conta de usuário existente, é fundamental compreender que alguns comandos falharão se o usuário alvo estiver logado no sistema no momento (como a tentativa de alterar o nome de login/username da conta).

Outras modificações não impedirão a execução do comando, mas só entrarão em vigor após o usuário encerrar a sessão atual (logout) e realizar um novo login. Por exemplo, ao modificar os grupos suplementares de uma conta, esses novos privilégios e associações não estarão disponíveis para o usuário até que uma nova sessão de login seja estabelecida.

Em ambos os casos, dominar o uso dos comandos who, w e last é indispensável para que o administrador audite quem está ativo na máquina antes de aplicar alterações estruturais.

Parâmetros do Comando usermod

Opção Curta Opção Longa Descrição Técnica
-c COMENTÁRIO — Altera o valor do campo de comentário ou GECOS da conta (ex: nome completo).
-d DIRETÓRIO --home DIRETÓRIO Define um novo caminho de diretório home para o usuário.
-e DATA --expiredate DATA Ajusta ou define a data absoluta de expiração da conta de usuário.
-f DIRETÓRIO --inactive DIAS Configura o período de carência (inatividade) após o vencimento da senha.
-g GRUPO --gid GRUPO Modifica o grupo primário do usuário (por nome ou GID).
-G GRUPOS --groups GRUPOS Especifica uma lista de grupos suplementares (separados por vírgula).
-a --append Adiciona/Anexa novos grupos secundários (deve ser usado junto com -G).
-h --help Exibe o menu de ajuda rápida com a sintaxe do comando.
-l NOVO_NOME --login NOVO_NOME Modifica o nome de login (username) do usuário.
-L --lock Bloqueia a conta do usuário (insere um ! no shadow).
-s SHELL --shell SHELL Altera o shell de login padrão atribuído à conta.
-u NOVO_UID --uid NOVO_UID Modifica o ID numérico do usuário (UID).
-U --unlock Desbloqueia a conta do usuário, restabelecendo o acesso.
Risco de Arquivos Órfãos ao Alterar UID: Assim como nos grupos, alterar o UID de um usuário com a opção -u pode ser altamente problemático, pois todos os arquivos criados anteriormente por ele no disco **se tornarão órfãos** (exibindo apenas o UID numérico antigo). Por outro lado, alterar apenas o nome textual com -l não gera arquivos órfãos, já que o ID numérico permanece o mesmo.
Estratégia de Bloqueio de Contas (Lock): Excluir um usuário definitivamente com o comando userdel pode apagar ou deixar arquivos órfãos espalhados pelo servidor. Uma alternativa muito mais segura em processos de desligamento é apenas bloquear temporariamente a conta usando a flag -L. Isso impede qualquer login ou uso da conta imediatamente, mas preserva intacta a propriedade e o acesso aos arquivos associados a ela para futuras auditorias.

O Perigo Oculto da Flag -G

Existe uma pegadinha crucial na administração de grupos suplementares: se você invocar a opção -G **sem** a opção -a (append), você substituirá integralmente as filiações do usuário. Isso significa que você é obrigado a listar todos os grupos antigos que deseja manter na mesma linha de comando.

Esquecer de associar a flag -a fará com que o usermod remova acidentalmente o usuário de todos os grupos secundários anteriores aos quais ele pertencia.

Para apenas adicionar um novo grupo suplementar mantendo os atuais intactos, utilize obrigatoriamente a combinação de flags -aG. No exemplo abaixo, adicionamos a usuária jane (que já pertence a sales e research) ao grupo development de forma segura: 

root@localhost:~# usermod -aG development jane

16.3.7 Excluindo um Usuário (userdel)

O comando userdel é a ferramenta utilizada para remover contas de usuários do sistema operacional.

Ao optar por excluir um usuário, você deve tomar uma decisão administrativa crucial: remover ou preservar o diretório home do usuário. Os arquivos pessoais de um colaborador podem conter dados intelectuais vitais para a organização ou estar sujeitos a regulamentações legais de retenção por prazos específicos. Portanto, avalie esse cenário com muita cautela.

Aviso de Ação Irreversível: A menos que você possua rotinas consolidadas de backup de dados, uma vez executado o comando para apagar o usuário junto com suas respectivas pastas, não há como reverter a ação. Os arquivos serão permanentemente expurgados do disco.

Para remover estritamente os metadados e o registro do usuário jane (retirando-a do /etc/passwd e /etc/shadow), mas preservando intacto o seu diretório home em /home/jane, execute o comando de forma direta: 

root@localhost:~# userdel jane
Geração de Arquivos Órfãos: Fique ciente de que excluir um usuário mantendo a pasta home dele fará com que todos os arquivos ali contidos se tornem órfãos. O mapeamento textual sumirá e o comando ls -l passará a exibir apenas os antigos UID e GID numéricos como proprietários dos dados.

Se o objetivo for realizar um expurgo completo — removendo a conta do usuário, o diretório home associado e a caixa de entrada de e-mails local (mail spool) de forma simultânea —, utilize a opção de remoção recursiva -r: 

root@localhost:~# userdel -r jane
Aviso: Limitação da Flag -r O comando userdel -r limpará apenas os arquivos contidos dentro do diretório home do usuário e o seu respectivo arquivo no spool de e-mails. Se este usuário tiver criado ou assumido a propriedade de outros arquivos fora da sua home (como em diretórios compartilhados como /var/www/, /tmp/ ou /opt/), esses arquivos continuarão existindo no sistema operacional como arquivos órfãos e deverão ser localizados manualmente via comando find -nouser.
