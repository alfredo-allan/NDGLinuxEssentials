Módulo 17

Propriedade e Permissões

Entendendo a segurança de arquivos no Linux através do gerenciamento de donos, grupos e permissões de acesso.

17.1 Introdução

A definição correta da propriedade de arquivos (file ownership) é um pilar crítico para a segurança de qualquer sistema operacional Linux. Para garantir o isolamento e a proteção dos dados, cada arquivo e diretório no sistema possui obrigatoriamente um usuário dono (user owner) e um grupo dono (group owner) associados a ele.

Este capítulo aborda de maneira detalhada os mecanismos para especificar e alterar os donos e grupos de um arquivo.

O que será explorado

Controle de Acesso: Exploraremos o conceito de permissões em arquivos e diretórios, compreendendo como os privilégios de leitura, escrita e execução interagem com o sistema de arquivos.

Modificação de Privilégios: Aprenderemos as ferramentas práticas utilizadas para alterar essas permissões de acesso dinamicamente, adaptando a segurança às necessidades do ambiente.

Permissões Padrão (Default Permissions): Estudaremos como o sistema calcula e atribui de forma automática os privilégios iniciais a novos arquivos e diretórios no exato instante em que são criados.

17.2 Propriedade de Arquivos

Por padrão, os usuários são proprietários dos arquivos e diretórios que eles mesmos criam no sistema. Embora essa propriedade possa ser transferida, essa operação é restrita e exige privilégios administrativos (root).

É importante destacar que, embora a maioria dos comandos exiba o nome do proprietário em formato de texto (username), o kernel do sistema operacional gerencia e associa a propriedade internamente utilizando o identificador numérico do usuário, o UID.

Além do dono, cada arquivo possui obrigatoriamente um grupo proprietário. Por padrão, o grupo primário do usuário que cria o arquivo é atribuído como o grupo dono deste novo elemento. Os usuários comuns têm permissão para alterar o grupo proprietário de seus arquivos, mas apenas para outros grupos secundários aos quais eles próprios já pertençam. Assim como na propriedade de usuário, o Linux associa o grupo internamente pelo seu ID numérico, o GID, e não pelo nome em texto.

Efeito de Contas Removidas ou Modificadas: Como a propriedade é determinada estritamente pelo UID e GID gravados nos metadados do arquivo, alterar o UID de um usuário (ou excluir a conta dele) fará com que seus arquivos fiquem sem um dono textual correspondente. Quando não houver um UID no arquivo /etc/passwd que coincida com o ID gravado no arquivo, o sistema exibirá o número bruto do UID no output de listagem. O mesmo comportamento ocorre para grupos órfãos em relação ao /etc/group.

Identificando suas Credenciais de Sessão: O Comando id

O comando id é extremamente útil para verificar qual conta de usuário está operando a sessão atual do terminal e quais grupos estão disponíveis para uso imediato. A saída deste comando expressa as identidades tanto por nomes textuaisamp; quanto por seus respectivos mapeamentos numéricos.

A execução padrão exibe o UID do usuário corrente, seguido pelo GID do seu grupo primário e a listagem de todos os grupos suplementares vinculados: 

sysadmin@localhost:~$ id
uid=1001(sysadmin) gid=1001(sysadmin) groups=1001(sysadmin),4(adm),27(sudo),1005(research),1006(development)

O output acima detalha que o usuário possui o UID 1001 vinculado ao nome sysadmin. Demonstra também que seu grupo primário possui o GID 1001 (grupo sysadmin).

O fato de a conta de usuário e o grupo primário compartilharem exatamente o mesmo nome e ID numérico evidencia que o sistema adota a arquitetura de Grupo Privado de Usuário (UPG). Adicionalmente, este usuário é membro de quatro grupos suplementares: adm (GID 4), sudo (GID 27), research (GID 1005) e development (GID 1006).

Criação e Listagem de Metadados

Quando um arquivo é gerado, ele herda o usuário atual e o grupo primário ativo da sessão. Se o usuário sysadmin do cenário anterior rodar o comando touch para criar um arquivo de teste, a propriedade será atribuída ao usuário sysadmin e ao grupo sysadmin: 

sysadmin@localhost:~$ touch /tmp/filetest1
sysadmin@localhost:~$ ls -l /tmp/filetest1
-rw-rw-r--. 1 sysadmin sysadmin 0 Oct 21 10:18 /tmp/filetest1

As regras de propriedade aplicam-se integralmente aos arquivos ocultos do sistema (aqueles cujo nome inicia com um caractere de ponto .). Para listá-los, adicionamos a flag -a ao utilitário de listagem.

Lembre-se de que as duas primeiras entradas ocultas retornadas correspondem ao diretório atual (.) e ao diretório pai imediatamente superior (..). O comando ls -la consolida a exibição de todas as pastas e arquivos ocultos do ambiente corrente:

17.3 Alterando Grupos Dinamicamente

Se você sabe de antemão que o arquivo ou diretório que está prestes a criar deve pertencer a um grupo diferente do seu grupo primário atual, você pode utilizar o comando newgrp para alterar temporariamente o seu grupo primário de sessão. 

newgrp nome_do_grupo

Enquanto o comando id lista informações detalhadas de identidade (incluindo UIDs e GIDs numéricos), se você estiver interessado apenas em saber textualmente a quais grupos sua conta pertence, pode executar de forma simplificada o comando groups: 

sysadmin@localhost:~$ groups
sysadmin adm sudo research development

A saída do comando groups não é tão detalhada quanto a do id, mas ela fornece exatamente a informação necessária para mapear quais são os grupos válidos para os quais você pode migrar utilizando o utilitário newgrp.

Por outro lado, o comando id é ideal para auditar se a transição de grupo do comando newgrp foi bem-sucedida, já que ele discrimina explicitamente qual é o grupo primário ativo no exato momento da checagem.

Por exemplo, se o usuário sysadmin planeja criar um arquivo cuja propriedade deve pertencer ao grupo research (que não é o seu grupo primário padrão), ele pode invocar o newgrp e validar a alteração com o id antes de criar o arquivo: 

sysadmin@localhost:~$ id
uid=1001(sysadmin) gid=1001(sysadmin) groups=1001(sysadmin),4(adm),27(sudo),1005(research),1006(development)
sysadmin@localhost:~$ newgrp research
sysadmin@localhost:~$ id
uid=1001(sysadmin) gid=1005(research) groups=1005(research),4(adm),27(sudo),1001(sysadmin),1006(development)

De acordo com o histórico dos comandos acima, inicialmente o GID primário do usuário era 1001 (grupo sysadmin). Após a execução do newgrp research, o GID primário da sessão ativa passou a ser o 1005 (grupo research).

Como consequência direta dessa alteração de contexto, se o usuário criar um novo arquivo agora e listar seus metadados, a propriedade do grupo herdada refletirá o grupo research: 

sysadmin@localhost:~$ touch /tmp/filetest2
sysadmin@localhost:~$ ls -l /tmp/filetest2
-rw-r--r--. 1 sysadmin research 0 Oct 21 10:53 /tmp/filetest2
Mecanismo de Subshell: O comando newgrp funciona abrindo um novo shell (subshell) sobreposto à sessão atual. Enquanto o usuário permanecer operando dentro desse subshell, o grupo primário modificado continuará ativo. Para encerrar essa sessão temporária e retornar instantaneamente ao grupo primário original do sistema, basta deslogar do subshell executando o comando exit: 
sysadmin@localhost:~$ id
uid=1001(sysadmin) gid=1005(research) groups=1005(research),4(adm),27(sudo),1001(sysadmin),1006(development)
sysadmin@localhost:~$ exit
exit
sysadmin@localhost:~$ id
uid=1001(sysadmin) gid=1001(sysadmin) groups=1001(sysadmin),4(adm),27(sudo),1005(research),1006(development)
Considere Isto: Alteração Permanente de Grupo Primário O comando newgrp altera o grupo apenas de forma volátil durante a sessão corrente. Se a necessidade administrativa for alterar o grupo primário de um usuário de forma definitiva em sua tabela cadastral, são necessários privilégios do administrador (root) para invocar o utilitário usermod com a opção de grupo primário (-g):
root@localhost:~# usermod -g nome_do_grupo nome_do_usuario

17.4 Alterando o Grupo Proprietário (chgrp)

Para alterar o grupo proprietário de um arquivo ou diretório já existente no sistema, utiliza-se o comando chgrp (change group). 

chgrp nome_do_grupo arquivo

Quando executado pelo superusuário root, o comando chgrp pode transferir a propriedade de qualquer arquivo para absolutamente qualquer grupo do sistema.

No entanto, quando operado por um usuário comum sem privilégios administrativos, o comando possui uma restrição de segurança: ele só permite alterar o grupo do arquivo para um grupo secundário ao qual o próprio usuário já pertença. Veja o exemplo: 

sysadmin@localhost:~$ touch sample
sysadmin@localhost:~$ ls -l sample
-rw-rw-r-- 1 sysadmin sysadmin 0 Oct 23 22:12 sample
sysadmin@localhost:~$ chgrp research sample
sysadmin@localhost:~$ ls -l sample
-rw-rw-r--. 1 sysadmin research 0 Oct 23 22:12 sample
Operação Não Permitida: Se um usuário tentar modificar o grupo proprietário de um arquivo do qual ele não é o dono (ou tentar atribuir um grupo ao qual não pertence), o sistema operacional abortará a ação exibindo uma mensagem de erro de permissão negada: 
sysadmin@localhost:~$ chgrp development /etc/passwd
chgrp: changing group of '/etc/passwd': Operation not permitted

Alterações Recursivas com a Opção -R

Para aplicar a mudança de grupo em toda uma estrutura de diretórios de forma massiva, utiliza-se a opção recursiva -R (obrigatoriamente em maiúsculo).

O comando demonstrado no exemplo abaixo altera simultaneamente o grupo proprietário da pasta test_dir e de todos os arquivos, subpastas e elementos contidos dentro dela: 

sysadmin@localhost:~$ chgrp -R development test_dir
Considere Isto: Diagnósticos Detalhados com o stat Embora a flag -l do comando ls permita visualizar os donos do arquivo, o Linux disponibiliza uma ferramenta muito mais profunda para auditar metadados, permissões e propriedades: o comando stat.

O utilitário stat expõe radiografias minuciosas do arquivo, exibindo os registros de propriedade simultaneamente pelo nome textual e pelo ID numérico (UID/GID), além de carimbos de data detalhados (Access, Modify, Change): 
sysadmin@localhost:~$ stat /tmp/filetest1
  File: `/tmp/filetest1'
  Size: 0         	Blocks: 0          IO Block: 4096   regular empty file
Device: fd00h/64768d	Inode: 31477       Links: 1
Access: (0664/-rw-rw-r--)  Uid: ( 1001/sysadmin)   Gid: ( 1001/sysadmin)

17.5 Alterando o Usuário Proprietário (chown)

O comando chown (change owner) permite alterar o usuário proprietário de arquivos e diretórios. Por questões rígidas de segurança do kernel, um usuário comum não pode doar ou transferir a propriedade de seus próprios arquivos para outro usuário; essa operação de mudança de dono exige obrigatoriamente privilégios de superusuário (root).

No entanto, o comando chown é extremamente versátil e também aceita a modificação do grupo proprietário, uma ação que pode ser realizada tanto pelo root quanto pelo atual dono do arquivo.

Existem três métodos principais para estruturar a sintaxe do comando chown:

Método 1: Alterar estritamente o Usuário Proprietário

Este método atualiza apenas o dono do arquivo, mantendo o grupo original intacto (operação exclusiva do root):

chown usuario /caminho/do/arquivo

Exemplo de execução prática realizada pelo administrador:

root@localhost:~# chown jane /tmp/filetest1
root@localhost:~# ls -l /tmp/filetest1
-rw-rw-r-- 1 jane sysadmin 0 Dec 19 18:44 /tmp/filetest1

Método 2: Alterar Usuário e Grupo Simultaneamente

Para modificar ambos os campos em uma única linha de comando (operação que também exige privilégios de root), separamos o nome do usuário e do grupo utilizando um caractere de **dois-pontos** (:) ou um **ponto** (.): 

chown usuario:grupo /caminho/do/arquivo
chown usuario.grupo /caminho/do/arquivo

Exemplo de execução prática:

root@localhost:~# chown jane:users /tmp/filetest2
root@localhost:~# ls -l /tmp/filetest2
-rw-r--r-- 1 jane users 0 Dec 19 18:53 /tmp/filetest2

Método 3: Alterar estritamente o Grupo Proprietário

Se um usuário comum não possui privilégios de root, ele pode usar este terceiro método para modificar apenas o grupo de seus arquivos, comportando-se de maneira idêntica ao utilitário chgrp. Para isso, basta omitir o usuário e adicionar um caractere de dois-pontos ou ponto como **prefixo** antes do nome do grupo: 

chown :grupo /caminho/do/arquivo
chown .grupo /caminho/do/arquivo

Veja o exemplo abaixo executado com o perfil comum da usuária jane:

jane@localhost:~$ chown .users /tmp/filetest1
jane@localhost:~$ ls -l /tmp/filetest1
-rw-rw-r-- 1 jane users 0 Dec 19 18:44 /tmp/filetest1
Dica de Escopo Recursivo: Assim como no comando chgrp, você pode adicionar a flag recursiva -R (em maiúsculo) ao comando chown para aplicar as novas regras de usuário e grupo a uma pasta e a todos os subdiretórios e arquivos contidos no interior dela de forma massiva.

17.6 Permissões de Arquivos e Diretórios

A saída gerada pelo comando ls -l exibe um conjunto inicial de **dez caracteres** no começo de cada linha. Esses caracteres são metadados que indicam o tipo do arquivo e os privilégios de acesso associados. Veja o exemplo: 

root@localhost:~# ls -l /etc/passwd
-rw-r--r--. 1 root root 4135 May 27 21:08 /etc/passwd

1. Tipo de Arquivo (File Type)

O **primeiro caractere** da string de dez posições identifica a natureza e o tipo do arquivo:

-rw-r--r-- 1 root root 4135 May 27 21:08 /etc/passwd
Caractere Tipo de Arquivo Descrição Técnica
- Arquivo comum Arquivo regular que pode estar vazio, conter texto plano ou dados binários executáveis.
d Diretório Pasta de sistema que armazena os nomes de outros arquivos e os ponteiros de inodes para eles.
l Link simbólico Atalho de sistema que aponta (refere-se) para o caminho de outro arquivo ou diretório.
b Dispositivo de bloco Arquivos de hardware onde o fluxo de dados é lido/gravado em blocos (ex: discos rígidos, SSDs).
c Dispositivo de caractere Arquivos de hardware com fluxo de dados lido/gravado byte a byte (ex: terminais tty, modems).
p Pipe (FIFO) Canal de comunicação sequencial que permite direcionar o output de um processo como input de outro.
s Socket Ponto de extremidade de rede ou local que permite a comunicação bidirecional síncrona entre processos.
Nota do Administrador: Embora todos os tipos acima existam na arquitetura do sistema de arquivos, no dia a dia operacional você raramente encontrará tipos diferentes de arquivos comuns (-), diretórios (d) e links (l), a menos que realize auditorias avançadas dentro da pasta de hardware do kernel, o diretório /dev.

2. Classes de Permissões (Permission Groups)

Os **nove caracteres seguintes** representam os privilégios reais. Quando um processo invocado por um usuário tenta ler, gravar ou rodar um elemento, o kernel faz uma checagem sequencial e excludente dividida em três classes ordenadas de papéis: 

-rw-r--r-- 1 root root 4135 May 27 21:08 /etc/passwd
  • Usuário Proprietário (User / Owner): Corresponde aos caracteres **2, 3 e 4**. Se o usuário que disparou o comando for o dono legítimo do arquivo, o kernel aplica exclusivamente esta triade de permissões e ignora o resto.
  • Grupo Proprietário (Group): Corresponde aos caracteres **5, 6 e 7**. Se o usuário não for o dono, mas fizer parte do grupo do arquivo, o kernel valida o acesso estritamente baseado nestas permissões.
  • Outros (Others / World): Corresponde aos caracteres **8, 9 e 10**. Esta classe abrange qualquer outra conta que não seja dona do arquivo e que também não pertença ao grupo proprietário dele.

3. Os Tipos de Acesso (Permission Types)

Cada um dos três grupos possui três bits básicos de controle (r para leitura, w para escrita, x para execução). Se a permissão estiver concedida, a letra correspondente é exibida; caso contrário, um hífen (-) indica a ausência do privilégio.

A interpretação exata desses direitos varia sensivelmente se o alvo for um arquivo ou um diretório estrutural:

Permissão Impacto em Arquivos Impacto em Diretórios
Leitura (r) Permite que processos leiam, visualizem e copiem o conteúdo interno do arquivo. Permite listar os nomes dos arquivos contidos dentro da pasta (ex: usando o comando ls).
Escrita (w) Permite modificar, salvar alterações ou truncar o conteúdo interno do arquivo.
Nota: Exige a permissão r para funcionar corretamente. 		Permite adicionar, remover, criar ou renomear arquivos e subpastas dentro do diretório.
Nota: Exige a permissão x para funcionar.
Execução (x) Permite mapear o arquivo na memória e executá-lo diretamente como um processo binário ou script. Permite que o usuário acesse a pasta (via comando cd) e utilize o caminho em caminhos absolutos/relativos para acessar arquivos internos.

17.7 Compreendendo as Permissões na Prática

As descrições abstratas dos tipos de permissões isoladas são úteis, mas sozinhas elas não oferecem uma visão clara de como o subsistema de segurança do Linux se comporta em cenários reais e encadeados.

Para compreender a fundo a mecânica de herança, restrição e travessia de caminhos, analisaremos uma série de cenários baseados na árvore de diretórios e nas permissões mapeadas abaixo:

Mapeamento Estrutural do Ambiente

Considere as propriedades vigentes para a raiz, o diretório de dados e o arquivo de teste:

drwxr-xr-x. 17 root root 4096 23:38 /
drwxr-xr-x. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

As informações estruturais revelam a seguinte hierarquia:

  • A Linha 1 representa o diretório raiz (/). Ele pertence ao usuário root, ao grupo root e possui permissões rwxr-xr-x.
  • A Linha 2 representa o diretório /data, que está aninhado diretamente sob a raiz. Ele também pertence ao usuário root, ao grupo root e adota as permissões rwxr-xr-x.
  • A Linha 3 representa o arquivo regular abc.txt, armazenado fisicamente dentro do diretório /data. Este arquivo pertence ao usuário bob, ao grupo bob e está configurado com os privilégios rwxr-xr--.
O que observar a seguir: Guarde este mapa mental de permissões. Nas próximas seções do curso, utilizaremos esta exata estrutura para testar o que acontece quando diferentes usuários (como o próprio bob, o root ou terceiros da classe others) tentam ler, excluir, editar ou rodar esse arquivo.

17.7.1 Cenário #1 - Acesso a Diretórios

Pergunta de Análise: Com base na estrutura de privilégios apresentada abaixo, qual nível de acesso real o usuário bob teria sobre o seu próprio arquivo abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
drwxr-xr--. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Técnica e Resolução do Caso

A resposta correta é: O usuário bob não terá NENHUM ACESSO ao arquivo abc.txt. Ele receberá uma mensagem de "Permissão Negada" (Permission Denied) ao tentar ler, gravar ou executar o arquivo.

Este cenário ilustra uma das pegadinhas mais comuns e cruciais da segurança em sistemas Linux: a travessia da árvore de diretórios.

Análise Passo a Passo do Bloqueio:
  1. Para que qualquer usuário consiga interagir com um arquivo no disco, ele precisa primeiro conseguir **atravessar** todos os diretórios do caminho (path) que levam até o arquivo. Conforme estudado na seção anterior, a permissão necessária para entrar/atravessar uma pasta é a de Execução (x).
  2. Analisando o diretório pai /data, vemos que ele pertence ao usuário root e ao grupo root. Como o usuário bob não é o root e também não pertence ao grupo root, ele cai automaticamente na classe dos Outros (others).
  3. Observando os três últimos caracteres do diretório /data (r--), vemos que a permissão da classe others concede apenas privilégio de Leitura (r) e nega a Execução (-).

Como o diretório /data carece da permissão x para terceiros, o usuário bob está impedido de dar um comando cd /data ou de referenciar qualquer objeto abaixo dele.

Embora o arquivo abc.txt seja de propriedade do próprio bob e possua permissões máximas de leitura, escrita e execução para ele (rwx), a barreira imposta pelo diretório pai bloqueia o acesso por completo. O único privilégio que bob mantém sobre a pasta /data devido ao bit r é listar o nome de texto dos arquivos contidos nela (via comando ls /data), mas ele será incapaz de ler os conteúdos, ver metadados ou acessar o arquivo.

17.7.1.1 Cenário #1 - Resposta Oficial

Pergunta de Revisão: Com base nas informações fornecidas, qual acesso o usuário bob teria sobre o arquivo abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
drwxr-xr--. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Correta: Nenhum.

Explicação Detalhada

Inicialmente, pode parecer que o usuário bob seria capaz de visualizar os conteúdos do arquivo abc.txt, bem como copiá-lo, modificar suas informações internas e executá-lo diretamente como um programa. No entanto, essa conclusão errônea ocorre quando olhamos **unicamente** para as permissões isoladas do arquivo em si (que neste caso estão configuradas como rwx para o proprietário).

Para realizar qualquer interação prática com o arquivo, o usuário deve ser capaz de acessar e "entrar" no diretório pai /data primeiro.

As permissões aplicadas a bob para a pasta /data correspondem à classe dos Outros (others), cujos bits estão como r--. Isso indica que ele não possui direitos de travessia e não pode sequer utilizar o comando cd para entrar no diretório.

Se a permissão de execução (--x) estivesse concedida para a classe de terceiros no diretório, bob conseguiria passar pela pasta, fazendo com que as permissões nativas do próprio arquivo abc.txt passassem a valer normalmente.

Lição Aprendida (Lesson Learned): As permissões de **todos os diretórios pai** em uma estrutura de caminhos devem ser rigorosamente analisadas antes de se avaliar os privilégios específicos configurados em um arquivo final.

17.7.2 Cenário #2 - Visualizando Conteúdos de Diretórios

Pergunta de Análise: Com base na estrutura de privilégios apresentada abaixo, quem está habilitado a utilizar o comando ls para exibir os nomes dos arquivos contidos dentro da pasta /data (ls /data)? 

drwxr-xr-x. 17 root root 4096 23:38 /
drwxr-xr--. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Técnica e Resolução do Caso

A resposta correta é: Qualquer usuário do sistema operacional Linux pode listar o conteúdo do diretório /data.

Para compreender o motivo pelo qual o acesso à listagem é irrestrito neste cenário, devemos analisar os privilégios aplicados a cada classe de usuário na pasta /data:

Análise por Classes de Usuários

  • O usuário root: Sendo o proprietário da pasta (root) com permissões rwx, ele possui acesso total para listar, modificar e entrar no diretório.
  • Membros do grupo root: Possuem a permissão r-x (leitura e execução), o que permite listar o conteúdo e navegar para dentro da pasta.
  • Qualquer outro usuário (incluindo bob): Cai na classe dos Outros (others). Como os três últimos caracteres do diretório /data estão configurados como r--, a permissão de Leitura (r) está explicitamente concedida a terceiros.
Impacto do bit "r" sem o bit "x": Como a classe others possui o bit r, usuários comuns como bob conseguem ler a tabela de nomes da pasta, fazendo com que o comando ls /data retorne com sucesso a string abc.txt.

Contudo, devido à ausência do bit de execução (x) para essa classe, se o usuário tentar visualizar metadados detalhados (como rodar ls -l /data), o sistema exibirá uma série de pontos de interrogação (?) no lugar do tamanho, permissões e donos, pois o kernel bloqueia o acesso aos inodes dos arquivos internos.

17.7.2.1 Cenário #2 - Resposta Oficial

Pergunta de Revisão: Com base nas informações fornecidas, quem pode utilizar o comando ls para exibir os conteúdos do diretório /data (ls /data)?

Explicação Detalhada

Tudo o que é exigido de um usuário para conseguir visualizar os nomes dos elementos contidos em um diretório é a permissão de Leitura (r) na pasta alvo (além da capacidade técnica de atravessar e acessar os diretórios pai anteriores).

A permissão de execução (x) concedida para todas as classes de usuários no diretório raiz (/) significa que qualquer conta do sistema pode utilizar a raiz como parte inicial de caminhos estruturais. Portanto, todos conseguem passar pela raiz para alcançar o nível do diretório /data.

Uma vez que chegam ao destino, a presença do bit de leitura (r) na classe others da pasta /data assegura que qualquer pessoa possa invocar o comando ls com sucesso para listar os arquivos locais. Isso inclui a visualização de metadados ocultos, fazendo com que o comando ls -a também funcione normalmente.

Contudo, vale reforçar: para conseguir extrair detalhes adicionais e estruturais dos arquivos (como rodar um ls -l), o diretório exigiria obrigatoriamente a permissão complementar de Execução (x). Sendo assim, embora o usuário root e os membros do grupo root possuam esse nível de privilégio no diretório /data, nenhum outro usuário comum conseguirá rodar o comando ls -l /data sem gerar inconsistências no output.

Lição Aprendida (Lesson Learned): A permissão de leitura (r) em um diretório permite estritamente que um usuário visualize e liste os nomes textuais dos arquivos contidos nele.

17.7.3 Cenário #3 - Excluindo Conteúdos de Diretórios

Pergunta de Análise: Com base na estrutura de privilégios e metadados apresentada abaixo, quem possui a atribuição técnica de conseguir deletar/remover o arquivo /data/abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
drwxrw-rw-. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Técnica e Resolução do Caso

A resposta correta é: Apenas o usuário root e os membros do grupo root conseguem deletar o arquivo. O usuário bob NÃO pode deletar seu próprio arquivo.

Este cenário traz à tona um dos conceitos mais contraintuitivos, porém fundamentais, do gerenciamento de permissões POSIX no Linux: a exclusão de um arquivo depende das permissões do diretório pai, e não do arquivo em si.

Por que o proprietário bob não pode deletar o arquivo?
  1. Apagar um arquivo significa, na estrutura interna do sistema de arquivos, remover o ponteiro com o nome dele de dentro da tabela de registros da pasta pai. Portanto, a exclusão é tecnicamente uma operação de modificação/escrita no diretório.
  2. Para conseguir alterar um diretório, o usuário precisa de duas permissões combinadas nele: Escrita (w) para apagar a entrada, e Execução (x) para conseguir entrar e alcançar aquela tabela.
  3. Avaliando a pasta /data, os bits de permissão para a classe others (onde o usuário bob se enquadra) estão definidos como rw-. Ou seja, a classe possui leitura e escrita, mas carece do bit de execução (x).

Pelo fato de o diretório /data não possuir o bit de execução (x) para terceiros, o kernel bloqueia a travessia de bob. Ele é incapaz de consolidar a gravação que removeria o arquivo do disco.

O usuário root e os integrantes do grupo principal root ignoram essa barreira por possuírem privilégios explícitos de travessia e gravação no diretório pai (rwx para o dono, rwx para o grupo).

17.7.3.1 Cenário #3 - Resposta Oficial

Pergunta de Revisão: Com base nas informações fornecidas, quem pode deletar o arquivo /data/abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
drwxrw-rw-. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Correta: Apenas o usuário root.

Explicação Detalhada

Um usuário não precisa de **nenhuma permissão no arquivo em si** para conseguir deletá-lo. Na verdade, o que se exige para remover um arquivo é a permissão de Escrita (w) no diretório onde o arquivo está fisicamente armazenado. Com base estritamente nisso, pareceria em um primeiro momento que todos os usuários seriam capazes de deletar o arquivo /data/abc.txt, já que todos possuem a permissão w na pasta.

No entanto, para conseguir excluir um arquivo, você também deve ser perfeitamente capaz de acessar e "entrar" na pasta correspondente. Como apenas o usuário root possui a permissão de Execução (x) no diretório /data, apenas ele consegue entrar de fato naquela estrutura para efetuar a remoção de arquivos locais.

Lição Aprendida (Lesson Learned): A permissão de escrita (w) confere ao usuário o direito de deletar arquivos de um diretório, **mas apenas se** o usuário também detiver a permissão de execução (x) sobre esse mesmo diretório.

17.7.4 Cenário #4 - Lendo Arquivos Específicos

Pergunta de Análise (Verdadeiro ou Falso): Com base na estrutura de privilégios apresentada abaixo, o usuário bob conseguirá executar com sucesso o comando more /data/abc.txt para ler o conteúdo deste arquivo? 

drwxr-xr-x. 17 root root 4096 23:38 /
dr-xr-x--x. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Técnica e Resolução do Caso

A resposta correta é: VERDADEIRO. O usuário bob conseguirá ler o arquivo com sucesso.

Para entender o sucesso dessa operação, vamos analisar o comportamento do kernel passo a passo em relação ao caminho fornecido:

Análise da Travessia e Leitura:
  1. Passagem pela pasta /data: O usuário bob cai na classe others em relação ao diretório /data. Os três últimos caracteres da pasta são --x. Isso significa que, embora ele não tenha permissão de leitura (r) ou escrita (w) na pasta, ele **possui o bit de execução (x)**. Esse bit é o suficiente para permitir que ele atravesse o diretório para acessar um objeto lá dentro.
  2. Acesso ao arquivo abc.txt: Uma vez que o bit x do diretório pai permitiu que bob chegasse até o arquivo, as permissões do próprio arquivo passam a ser avaliadas. Como bob é o dono (owner) do arquivo e possui permissões rwx nele, o bit de Leitura (r) está ativo, permitindo que o utilitário more leia o conteúdo perfeitamente.

Este cenário consolida um conceito essencial: o bit de execução (x) isolado em um diretório atua como uma permissão de "passagem às escuras".

O usuário bob não consegue listar o que tem dentro da pasta usando um comando genérico de listagem (um ls /data resultaria em Permission Denied devido à falta do bit r na pasta), mas se ele souber exatamente o nome do arquivo que procura (abc.txt), ele conseguirá acessá-lo e lê-lo sem problemas.

17.7.4.1 Cenário #4 - Resposta Oficial

Pergunta de Revisão (Verdadeiro ou Falso): Com base nas informações fornecidas, o usuário bob conseguiria executar com sucesso o comando more /data/abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
dr-xr-x--x. 10 root root 128  03:38 /data
-rwxr-xr--.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Correta: Verdadeiro.

Explicação Detalhada

Conforme mencionado anteriormente, para conseguir interagir com qualquer arquivo, o usuário precisa obrigatoriamente ter direitos de acesso ao diretório onde ele reside. Para fins de travessia e alcance, o acesso a uma pasta exige **estritamente a permissão x**. Embora a permissão r seja útil para listar e descobrir os arquivos locais, ela não é obrigatória para conseguir "entrar" na estrutura e abrir um arquivo cujo caminho exato já é conhecido.

Quando o comando more /data/abc.txt é disparado por bob, o kernel realiza uma checagem sequencial de três etapas de validação:

  • Permissão x no diretório raiz (/).
  • Permissão x no diretório de dados (/data).
  • Permissão r no arquivo final (abc.txt).

Como o usuário bob contempla todos esses requisitos nas respectivas classes envolvidas, o comando é executado com sucesso e o conteúdo é impresso na tela.

Lição Aprendida (Lesson Learned): A permissão de execução (x) é necessária para conseguir transitar por dentro de um diretório, mas a permissão de leitura (r) na pasta é totalmente dispensável, a menos que você necessite listar e visualizar o índice de conteúdos contidos nela.

17.7.5 Cenário #5 - A Complexidade de Usuários e Grupos

Pergunta de Análise (Verdadeiro ou Falso): Com base na estrutura de privilégios apresentada abaixo, o usuário bob conseguirá executar com sucesso o comando more /data/abc.txt?

Nota Importante: Repare que o diretório /data possui usuários e grupos proprietários **diferentes** dos cenários anteriores. 

drwxr-xr-x. 17 root root    4096 23:38 /
dr-xr-x---. 10 sue  payroll 128  03:38 /data
-rwxr-xr--.  1 bob  bob     100  21:08 /data/abc.txt

Resposta Técnica e Resolução do Caso

A resposta correta é: FALSO. O usuário bob NÃO conseguirá ler o arquivo e receberá um erro de "Permissão Negada".

Este cenário é excelente para demonstrar como o Linux avalia de forma estrita as classes de acesso. Para compreender o bloqueio, vamos analisar as permissões do diretório /data sob a perspectiva do usuário bob:

Análise das Permissões do Diretório:
  • Classe Usuário (Dono): O proprietário da pasta é a usuária sue, com privilégios r-x.
  • Classe Grupo: O grupo dono é o payroll, com privilégios r-x.
  • Classe Outros (others): Representada pelos três últimos caracteres (---). Esta é a classe na qual bob se enquadra.

Como os três últimos bits do diretório /data são hífens (---), a classe others tem **zero privilégios de acesso** (sem leitura, sem escrita e, crucialmente, sem execução).

Mesmo que o arquivo final /data/abc.txt pertença a bob e dê a ele privilégios totais de leitura (r), o kernel barra a operação logo na tentativa de inspecionar a pasta pai. bob é completamente incapaz de atravessar o diretório /data, fazendo com que o utilitário more falhe instantaneamente por falta de acesso ao caminho estrutural.

O Linux avalia as classes de acesso de forma hierárquica e condicional:

  • Se o bob for membro do grupo payroll: As permissões vigentes para ele sobre o diretório /data serão as da classe de grupo, ou seja, r-x. Nesse caso, a travessia é permitida e o comando more será executado com absoluto sucesso (já que ele também possui x na raiz e r no próprio arquivo).
  • Se o bob NÃO for membro do grupo payroll: Ele não corresponderá nem à dona (sue) e nem ao grupo proprietário (payroll), caindo na classe dos Outros (others). Como as permissões de terceiros estão configuradas como ---, ele terá o acesso negado e o comando falhará por completo.
Lição Aprendida (Lesson Learned): Você deve analisar as permissões de cada arquivo e diretório de forma individualizada, mantendo-se sempre ciente de quais grupos secundários e suplementares a conta de usuário faz parte no sistema operacional.

17.7.6 Cenário #6 - Prioridade de Permissões

Pergunta de Análise (Verdadeiro ou Falso): Com base na estrutura de privilégios apresentada abaixo, o usuário bob conseguirá executar com sucesso o comando more /data/abc.txt?

Nota Importante: Repare que a pasta e o arquivo possuem donos e grupos idênticos, mas os bits de permissão do arquivo abc.txt foram invertidos de propósito para testar a lógica do kernel. 

drwxr-xr-x. 17 root root 4096 23:38 /
dr-xr-x---. 10 bob  bob  128  03:38 /data
----rw-rwx.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Técnico-Conceitual

A resposta correta é: FALSO. O usuário bob NÃO conseguirá ler o arquivo e receberá erro de "Permissão Negada".

Este cenário ilustra de forma cirúrgica a **Regra de Correspondência Excludente** do Linux. Muitos iniciantes erram essa questão pensando: *"Ah, as permissões do grupo dão acesso à leitura (rw-) e as de outros dão acesso total (rwx), então o bob vai conseguir ler"*. No entanto, o kernel do Linux não soma ou acumula permissões das classes.

Como o Kernel Processa as Classes (Algoritmo de Checagem): Quando o usuário bob tenta abrir o arquivo abc.txt (após passar com sucesso pela pasta /data, já que ele é o dono dela e possui o bit x), o kernel faz a seguinte validação linear no arquivo:
  1. O usuário da sessão é o dono (User Owner) do arquivo? O kernel checa e vê que o UID do processo é igual ao UID dono do arquivo (ambos são bob). A correspondência foi encontrada!
  2. A consequência: No exato instante em que encontra a correspondência de dono, o kernel bloqueia a checagem e avalia apenas a trindade de bits do dono (caracteres 2, 3 e 4), ignorando completamente o que está definido para o grupo ou para os outros.
  3. O veredito: Os bits de permissão do usuário dono estão definidos como --- (zero privilégios). Portanto, mesmo havendo leitura nas outras classes, o acesso do proprietário é negado de forma explícita e imediata.

Portanto, devido a essa arquitetura de segurança, o usuário bob acaba sendo a **única conta comum no sistema inteiramente impedida de interagir com o arquivo**. Qualquer outro usuário aleatório do sistema operacional que caísse na classe others teria permissões completas de leitura, escrita e execução (rwx) sobre este objeto.

Obviamente, o usuário superusuário root ignora essas travas por possuir privilégios absolutos que sobrepõem o modelo padrão de checagem DAC (Discretionary Access Control).

17.7.6.1 Cenário #6 - Resposta Oficial

Pergunta de Revisão (Verdadeiro ou Falso): Com base nas informações fornecidas, o usuário bob conseguiria executar com sucesso o comando more /data/abc.txt? 

drwxr-xr-x. 17 root root 4096 23:38 /
dr-xr-x---. 10 bob  bob  128  03:38 /data
----rw-rwx.  1 bob  bob  100  21:08 /data/abc.txt

Resposta Correta: Falso.

Explicação Detalhada

Lembre-se da regra de ouro: se você for o proprietário (dono) de um arquivo, **as únicas permissões que o sistema checará e validará serão as permissões da classe de usuário**. Neste caso específico, os bits do proprietário no arquivo /data/abc.txt estão configurados como --- para bob.

Devido a essa característica algorítmica do kernel, os integrantes do grupo bob e a classe dos "Outros" (others) acabaram ficando com privilégios e níveis de acesso muito superiores aos do próprio criador do arquivo.

Lição Aprendida (Lesson Learned): Nunca conceda privilégios de acesso generosos ao grupo proprietário e à classe "others" sem antes aplicar, no mínimo, o mesmo nível ou um patamar superior de permissões ao usuário dono do arquivo.

17.8 Alterando Permissões (chmod)

O comando chmod (change mode) é o utilitário nativo utilizado para alterar as permissões e modos de acesso de arquivos e diretórios no ecossistema Linux.

Existem duas técnicas metodológicas distintas que podem ser aplicadas com este comando para definir os novos privilégios: a técnica simbólica (utilizando letras e operadores) e a técnica numérica (utilizando notação octal de três dígitos). ambas as abordagens compartilham a mesma sintaxe estrutural básica: 

chmod nova_permissao nome_do_arquivo
Requisito Crucial de Propriedade: Para que um usuário comum consiga alterar com sucesso as permissões de um objeto, ele precisa obrigatoriamente ser o dono (owner) legítimo do arquivo ou estar operando com os privilégios administrativos do superusuário root.

Arquivo de Cenário Base

Para ilustrar os exemplos práticos de aplicação de ambas as técnicas nas próximas seções, utilizaremos como base o seguinte arquivo genérico criado pelo usuário administrador: 

root@localhost:~# touch abc.txt
root@localhost:~# ls -l abc.txt
-rw-r--r-- 1 root root 0 Dec 19 18:58 abc.txt

17.8.1 O Método Simbólico

Se o seu objetivo é modificar apenas alguns bits específicos das permissões atuais, mantendo o restante intacto, o método simbólico costuma ser a abordagem mais simples e intuitiva. Com esta técnica, você pontua exatamente quais direitos deseja alterar, e os demais metadados do arquivo permanecem inalterados.

Para construir o argumento de modificação no método simbólico, você deve combinar obrigatoriamente **três tipos de informações** em uma string contínua:

Anatomia do Argumento Simbólico

1. Classe de Usuário (Quem) 2. Operador de Ação (Como) 3. Tipo de Permissão (O quê)
u : Usuário Dono (user)
g : Grupo Dono (group)
o : Outros (others)
a : Todos (all - u, g e o combinados) 		+ : Adiciona a permissão
- : Remove a permissão
= : Define exatamente a permissão (removerá as não citadas) 		r : Leitura (read)
w : Escrita (write)
x : Execução (execute)

Exemplo 1: Adicionar permissão de escrita ao Grupo

Para conceder ao grupo proprietário o direito de gravação no arquivo abc.txt, utilizamos o argumento g+w: 

root@localhost:~# chmod g+w abc.txt
root@localhost:~# ls -l abc.txt
-rw-rw-r-- 1 root root 0 Dec 19 18:58 abc.txt

Repare que apenas o bloco de permissões do grupo foi afetado. Todos os outros bits permaneceram exatamente iguais ao estado anterior.

Exemplo 2: Combinando Múltiplas Modificações

É possível encadear diferentes regras de modificação na mesma linha separando-as por uma **vírgula** (sem espaços). O exemplo abaixo adiciona o bit de execução ao dono e ao grupo (ug+x) e remove simultaneamente o bit de leitura da classe outros (o-r): 

root@localhost:~# chmod ug+x,o-r abc.txt
root@localhost:~# ls -l abc.txt
-rwxrwx--- 1 root root 0 Dec 19 18:58 abc.txt

Exemplo 3: Sobreescrita Absoluta com o Operador de Igualdade (=)

O operador = define de forma estrita as permissões informadas e **remove automaticamente** quaisquer outros bits daquela classe que não tenham sido mencionados na instrução.

Para fazer com que o usuário proprietário tenha estritamente permissões de leitura e execução, retirando seu privilégio de escrita corrente, rodamos o argumento u=rx: 

root@localhost:~# chmod u=rx abc.txt
root@localhost:~# ls -l abc.txt
-r-xrwx--- 1 root root 0 Dec 19 18:58 abc.txt

17.8.2 O Método Numérico (Octal)

O método numérico (também conhecido como método octal) é a abordagem mais eficiente e rápida quando se deseja redefinir completamente todas as permissões de um arquivo de uma só vez.

Ele se baseia no sistema de numeração octal, no qual cada um dos três tipos de permissões básicas recebe um valor numérico fixo com peso binário:

4 = Leitura (r) 2 = Escrita (w) 1 = Execução (x)

Tabela de Combinações Octais

Somando esses valores individuais, é possível representar qualquer combinação de privilégios para uma classe por meio de um único dígito de 0 a 7:

Número String Simbólica Soma Matemática Significado Técnico
7 rwx 4 + 2 + 1 Permissão total (Leitura, Escrita e Execução)
6 rw- 4 + 2 + 0 Leitura e Escrita
5 r-x 4 + 0 + 1 Leitura e Execução (comum para diretórios e binários)
4 r-- 4 + 0 + 0 Apenas Leitura
3 -wx 0 + 2 + 1 Escrita e Execução (raramente utilizado)
2 -w- 0 + 2 + 0 Apenas Escrita
1 --x 0 + 0 + 1 Apenas Execução (passagem para diretórios)
0 --- 0 + 0 + 0 Nenhum privilégio de acesso

Aplicação Prática da Tríade Octal

No argumento do comando chmod, passamos uma sequência exata de três números: o primeiro dígito define o dono (User), o segundo define o Grupo (Group) e o terceiro define Terceiros (Others).

Ao contrário do método simbólico, o método numérico **sobrescreve os nove bits simultaneamente**. Por esse motivo, o método simbólico é mais prático para ajustes pontuais, enquanto o numérico é ideal para modificações drásticas e completas.

Por exemplo, para configurar as permissões do arquivo abc.txt para que fiquem estritamente como rwxr-xr-- (Dono: 7, Grupo: 5, Outros: 4), executamos o seguinte comando: 

root@localhost:~# chmod 754 abc.txt
root@localhost:~# ls -l abc.txt
-rwxr-xr-- 1 root root 0 Dec 19 18:58 abc.txt
Considere Isto: Visualização Octal Direta com o stat Como estudado anteriormente, o utilitário stat fornece uma análise muito mais rica que o ls -l. Uma das grandes vantagens do seu uso na auditoria de segurança é que ele mapeia e exibe as permissões de forma simultânea nos dois formatos, incluindo a **notação octal de 4 dígitos** (onde o primeiro caractere representa bits especiais como SUID/SGID/Sticky, que serão vistos adiante): 
sysadmin@localhost:~$ stat /tmp/filetest1

Device: fd00h/64768d	Inode: 31477       Links: 1

17.9 Permissões Padrão e a Máscara umask

O comando umask (user mask) é um recurso interno do shell utilizado para determinar de forma automática os privilégios iniciais de acesso atribuídos a um arquivo ou diretório no exato instante de sua criação.

As permissões padrão finais são calculadas realizando-se uma **subtração lógica** do valor da máscara (umask) a partir das permissões máximas predefinidas pelo sistema. É crucial destacar que essas permissões máximas iniciais são diferentes para arquivos e diretórios:

  • Arquivos Regulares: Permissão máxima inicial de 666 (rw-rw-rw-). Por motivos severos de segurança de arquitetura, nenhum arquivo nasce com o bit de execução ativo por padrão no Linux. Para tornar um script executável, ele deve ser obrigatoriamente criado primeiro e depois modificado via chmod.
  • Diretórios/Pastas: Permissão máxima inicial de 777 (rwxrwxrwx). Os diretórios precisam do bit de execução (x) desde o nascimento para viabilizar os comandos de navegação e travessia (cd).

Consultando a Máscara Atual

Executar o comando umask sem argumentos expõe o valor restritivo configurado para a sessão corrente do shell:

sysadmin@localhost:~$ umask
0002

Anatomia detalhada dos quatro dígitos do output:

  • O primeiro dígito (0) indica apenas que o valor está expresso no sistema numérico octal.
  • O segundo dígito (0) determina quais permissões subtrair da classe do Usuário Dono.
  • O terceiro dígito (0) determina quais permissões subtrair da classe do Grupo Dono.
  • O quarto dígito (2) determina quais permissões subtrair da classe dos Outros (others).
Perfil de Máscara do Administrador: Contas de usuários diferentes costumam possuir máscaras distintas. Por padrão, o superusuário root adota uma política de criação muito mais restritiva que as contas de usuários comuns no Linux: 
root@localhost:~# umask
0022

Cenário Prático 1: Criação de Arquivos (Exemplo com umask 027)

Suponha que alteramos temporariamente a máscara para 027. A matemática aplicada para novos arquivos regulares deduzirá as permissões da seguinte forma:

Componente Representação Octal Mapeamento Simbólico Resultante
Permissão Máxima Base 666 rw- rw- rw-
Máscara Aplicada (Subtração) - 027 --- -w- rwx
Resultado Final do Arquivo 640 rw- r-- ---

Veja a validação da simulação no terminal:

sysadmin@localhost:~$ umask 027
sysadmin@localhost:~$ touch sample
sysadmin@localhost:~$ ls -l sample
-rw-r-----. 1 sysadmin sysadmin 0 Oct 28 20:14 sample

Cenário Prático 2: Criação de Diretórios (Exemplo com umask 027)

Adotando a mesma máscara de 027, a lógica de cálculo aplicada sobre os diretórios herdará o bit de execução máximo de partida:

Componente Representação Octal Mapeamento Simbólico Resultante
Permissão Máxima Base 777 rwx rwx rwx
Máscara Aplicada (Subtração) - 027 --- -w- rwx
Resultado Final do Diretório 750 rwx r-x ---

Veja a validação da simulação no terminal:

sysadmin@localhost:~$ umask 027
sysadmin@localhost:~$ mkdir test-dir
sysadmin@localhost:~$ ls -ld test-dir
drwxr-x---. 1 sysadmin sysadmin 4096 Oct 28 20:25 test-dir
Escopo Volátil da Sessão: A alteração manual do valor do umask feita diretamente na linha de comando possui efeito **volátil e temporário**, aplicando-se apenas aos elementos gerados de dentro daquela sessão específica do shell. Assim que um novo terminal ou subshell for iniciado, os valores padrões de fábrica do sistema serão restaurados automaticamente.

Se a necessidade administrativa consistir em tornar a alteração do umask permanente e definitiva para uma determinada conta de usuário, deve-se editar e adicionar a instrução de alteração no arquivo de configuração do perfil do shell do usuário, localizado em seu diretório home: o arquivo oculto .bashrc.
